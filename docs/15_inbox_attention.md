# Фаза 5. Inbox, уведомления и внимание, v0.2

> Статус: **v0.1 одобрена 2026-10-17** (ответы в §13). v0.2: веб-интерфейс — прежде всего админ-панель с отладкой (N9′, на подтверждении); кнопки в каналах сразу ставят вердикт. Это проактивная часть ассистента (01 §6): замечать ситуации, где нужно ваше внимание, спрашивать, напоминать, исследовать перед обращением, присылать сводки.
> Основание: модель знаний (Proposal, Verdict, виды `commitment`, `open_question`, `responsibility`), API (scopes, `/v1/inbox`), фаза 3 (события, джобы, вопросы агентов, `digest`), фаза 4 (каналы ввода).
> Главный принцип из требований: **уведомление — не цель; за ним всегда стоит ситуация в памяти, которую можно рассмотреть и разрешить.**

## 1. Словарь

| Понятие | Что это | Пример |
|---|---|---|
| **Attention item** | Запись в Inbox: ситуация, требующая человека, со ссылками на память и доступными действиями | конфликт сроков, вопрос агента, напоминание |
| **Kind** | Вид записи | `proposal`, `question`, `reminder`, `alert`, `digest` |
| **Attention profile** | Что важно пользователю: его обязанности и проекты (из утверждений `responsibility` о нём в Ledger), настройки: тихие часы, каналы, лимиты | «отвечаю за релизы Orion» |
| **Route** | Решение маршрутизатора по записи: кому, насколько срочно, в какой канал | «Алисе, сейчас, Telegram» |
| **Channel** | Модуль доставки и ответа: мессенджер, push, почта, веб, AI-клиент | Telegram-бот |
| **Seen checkpoint** | До какого момента пользователь уже всё видел; основа для «что нового с прошлого раза» | — |

## 2. Inbox — одна очередь ситуаций

| Вид | Откуда | Действия |
|---|---|---|
| `proposal` | Предложение изменения знаний ждёт вердикта | принять (вариант), с правкой, отклонить, отложить, исследовать |
| `question` | Агент спросил в ходе запуска (фаза 3) | ответить, выбрать вариант, отложить |
| `reminder` | Приближается срок обязательства; вопрос `open_question` висит долго; наступил `review_after` | отметить выполненным, перенести, перепроверить, открыть |
| `alert` | Запуск упал, бюджет исчерпан, источник отключился | открыть, повторить, отключить |
| `digest` | Сводка за период | открыть, отметить просмотренным |

- У каждой записи: ссылки на утверждения, предложения, запуски, источники; **почему** она появилась (цепочка причин); срок; состояние `new` → `seen` → `snoozed` / `resolved`.
- Отдельных «просто уведомлений» нет: любое сообщение в канал — это показ записи Inbox.
- Решение принимается в Ledger или в запуске (вердикт, ответ). Запись закрывается сама, когда ситуация разрешена, где бы это ни произошло.

## 3. Внимание: кому, когда, куда

Возможность модуля `attention.route@v1`: на вход — запись и профиль пользователя, на выход — маршрут.

| Решение | Варианты |
|---|---|
| Кому | Тем, кого ситуация касается: ответственным по связанным сущностям, автору исходной заметки, тому, от чьего имени работал агент; по умолчанию — всем пользователям инсталляции в Inbox, но push — только касающимся |
| Насколько срочно | `now` (push сейчас), `digest` (в ближайшую сводку), `silent` (только в Inbox) |
| Куда | Предпочтительный канал пользователя для этой срочности; запасной при отказе |

На что смотрит маршрутизатор:
- **Касается ли меня:** связанные сущности против моих обязанностей и проектов — а они сами знания в Ledger (`responsibility` обо мне). Профиль внимания поддерживается так же, как всё остальное.
- **Свойства ситуации:** риск (конфликт важнее нового факта), близость срока, затронуты ли мои обязательства, достоверность источника, кто автор.
- **Мои настройки:** тихие часы, лимит push в день, каналы.

Реализация по умолчанию — правила из конфига + опционально дешёвая классификация через `llm.complete`. Заменяется модулем.

## 4. Против спама

- Одна запись — одно сообщение на канал; повтор только как напоминание с растущим интервалом.
- Мелочи собираются в сводку, а не шлются по одной.
- Лимит push на пользователя в день; тихие часы; срочное в тихие часы — только если явно разрешено.
- Эскалация — только для срочного: нет реакции за N часов → следующий канал.
- «Исследовать перед обращением» (см. §6) снижает число пустых вопросов.

## 5. Каналы

Возможности модулей:

| Возможность | Что делает |
|---|---|
| `notify.send@v1` | Показать запись: текст, ссылка, кнопки действий |
| `notify.ask@v1` | Принять ответ в канале: нажатие кнопки, текстовый ответ, голосовой ответ |
| `notify.update@v1` | Обновить уже отправленное сообщение, когда ситуация разрешена в другом месте |

| Канал (модуль) | Кнопки | Ответ текстом или голосом | Заметки |
|---|---|---|---|
| Telegram-бот | inline-кнопки | да | Тот же бот, что для быстрого ввода; правка отправленного сообщения |
| Slack-бот | Block Kit | да | Для рабочей инсталляции; нужен публичный адрес для интерактивности |
| ntfy (push) | до 3 кнопок, `http`-кнопка вызывает действие ✅ | нет | Работают ли `http`-кнопки на iOS — не подтверждено ⚠️ |
| Web push (PWA) | да | через веб | На iOS — для установленного PWA |
| Email | ссылки | ответ письмом (опционально) | Для сводок |
| AI-клиенты (MCP) | карточки MCP Apps, где поддерживаются | да, в чате | Пользователь сам спрашивает «что у меня в Inbox?» |
| OpenClaw / Hermes | в их каналах | да | Два способа: их heartbeat опрашивает наш Inbox через MCP, или наш модуль шлёт сообщение через их MCP (`openclaw mcp serve` даёт `messages_send`) ⚠️ |

**Связка аккаунта канала с пользователем:** одноразовый код из веба или CLI («отправьте боту /link 4821»). Действия из канала выполняются от имени связанного пользователя и пишутся в аудит.

## 6. Исследовать перед обращением

(01 §6: «по событию дополнительно исследовать контекст, прежде чем обращаться ко мне».)

```yaml
attention:
  before_notify:
    - when: { kind: proposal, risk: conflict }
      run: investigate            # джоба из фазы 3
      max_wait: 30m               # не дождались — шлём как есть
```

Сначала агент дособирает контекст (кто и где ещё это обсуждал, что говорят достоверные источники), дополняет предложение и, возможно, предлагает вариант решения. Только потом уходит уведомление — уже с контекстом.

## 7. Сводка «что нового с прошлого раза»

- У каждого пользователя свой **seen checkpoint**; сводка — всё, что произошло после него, а не «за вчера».
- Содержимое: принятое новое знание (коротко), что ждёт решения, ближайшие сроки, что устарело или требует перепроверки, итоги фоновых запусков и сбои, расходы.
- Делается джобой `digest` (`llm.complete`) по событию расписания из конфига или по запросу («что нового?» в любом канале).
- Просмотр сводки сдвигает checkpoint.

## 8. Напоминания из памяти

| Источник в Ledger | Напоминание |
|---|---|
| `commitment` с `due` | За N дней до срока; в день срока; после — «выполнено или перенести?» |
| `open_question` с `waiting_on` | Висит дольше N дней → «напомнить человеку или закрыть?» |
| `review_after` | Наступил → `reverify` (агент) → предложение или напоминание |
| `status` устарел | Давно не подтверждался → вопрос |

Сроки напоминаний пересчитываются при изменении утверждения; планировщик выпускает события, dispatcher создаёт записи Inbox.

## 9. Веб-интерфейс — админ-панель

(По ревью N9 и QN2: «скорее админ-панель» + отладка, если что-то заглохло, + логи.) Повседневная работа идёт через каналы и AI-клиенты; веб нужен прежде всего для управления и диагностики. Модуль `ui.admin` (PWA), данные — из наблюдаемости фазы 6.

| Экран | Что |
|---|---|
| Здоровье | Состояние модулей, отставание dispatcher, курсоры источников и их «возраст», очередь задач, бюджеты |
| Запуски | Все запуски с фильтрами; зависшие и упавшие (dead-letter) — с кнопками повторить, отменить, написать агенту; шаги и вызовы инструментов запуска |
| События | Живая лента журнала с фильтрами; переход от события к запуску, предложению, источнику |
| Логи | Поиск по структурированным логам ядра и модулей, связанным по id запуска и события |
| Расходы | По аккаунтам, джобам, моделям, дням |
| Конфиг | Ревизии с diff, применить или откатить, предложения изменения конфига |
| Подключения | Источники, токены и клиенты, каналы и связка аккаунтов, аккаунты провайдеров |
| Аудит | Кто что принял, отклонил, поменял |
| Inbox и Explorer | Рабочие экраны для того, что неудобно в чате: было и стало, доказательства с переходом к месту в источнике, история и линия времени |

Детекторы «что-то заглохло» (курсор источника не двигается, запуск ждёт слишком долго, растёт dead-letter, бюджет на исходе, бэкап не прошёл) создают записи Inbox вида `alert`.

## 10. Решения на ревью

| ID | Решение |
|---|---|
| N1 | Один Inbox ситуаций: предложения, вопросы агентов, напоминания, тревоги, сводки. Каждая запись привязана к ситуации в памяти и несёт доступные действия; отдельных уведомлений нет |
| N2 | Маршрутизатор внимания решает кому, насколько срочно (сейчас, в сводку, тихо) и куда; опирается на обязанности пользователя из Ledger, свойства ситуации и настройки; модуль `attention.route@v1` |
| N3 | Каналы — модули `notify.send` / `notify.ask` / `notify.update`; кнопки вызывают те же действия API; примеры: Telegram, Slack, ntfy, web push, почта, AI-клиенты, OpenClaw / Hermes |
| N4 | Разрешить ситуацию можно где угодно; остальные каналы обновляются; повторное действие по решённой ситуации показывает текущее состояние |
| N5 | Против спама: одно сообщение на запись и канал, мелочи в сводку, лимит push в день, тихие часы, напоминания с растущим интервалом, эскалация только для срочного |
| N6 | Правило «исследовать перед обращением»: для выбранных ситуаций сначала запускается агент, и уведомление приходит с контекстом и вариантом решения |
| N7 | Сводка «что нового с прошлого раза» по личному checkpoint; по расписанию из конфига или по запросу в любом канале |
| N8 | Напоминания выводятся из памяти: сроки обязательств, зависшие вопросы, перепроверки, устаревшие статусы |
| N9 | Минимальный веб-интерфейс (PWA): Inbox, Explorer, Activity, Settings (заменено на N9′) |
| N9′ | Веб-интерфейс v1 — админ-панель: здоровье, запуски с повтором и отменой, лента событий, логи, расходы, ревизии конфига, подключения, аудит + Inbox и Explorer; детекторы «заглохло» создают тревоги в Inbox |

## 11. Вопросы

- Кнопки «принять / отклонить» в мессенджерах и push должны сразу ставить вердикт (предложено, всё пишется в аудит) или только открывать карточку в вебе?
