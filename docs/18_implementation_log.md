### M1. Ledger + API — готов

- Крейт `frood-ledger`: источники и доказательства, наблюдения, сущности (создание, слияние, разделение), утверждения как неизменяемые bitemporal-строки (`valid_*`, `recorded_*`), предложения с альтернативами, вердикты, флаги `contested` / `needs_verification`, связи, журнал.
- Инварианты в БД: текущее знание об утверждении не пересекается по valid-времени (exclusion constraint на `btree_gist`); журнал пишется под транзакционной advisory-блокировкой, поэтому позиции видны строго по порядку.
- Вердикт применяет альтернативу атомарно, предварительно заблокировав затронутые утверждения и проверив базу; устаревшая база → предложение `stale`, ошибка 409.
- Политики (M8, M11): свои новые факты пользователя без конфликта и слияния сущностей с уверенностью ≥ 0.9 принимаются автоматически, вердикт подписан `policy:<имя>`; настраивается секцией `policies` в `frood.yaml`.
- API `/v1`: `sources`, `evidence`, `observations`, `assertions` (фильтры `kind`, `entity`, `status`, `text`, `valid_at`, `as_of`, `slot.<имя>.<eq|gte|lt|in>`, курсор), `assertions/{id}` (+ `?as_of=&valid_at=`), `assertions/{id}/history`, `entities`, `proposals` (+ `Idempotency-Key`), `proposals/{id}/verdicts`, `journal`. Ошибки — RFC 9457.

**Проверено:** 35 тестов (8 интеграционных тестов Ledger, сквозной тест API, юнит-тесты), clippy `-D warnings`, живой прогон через curl: голосовая заметка → своё утверждение принято политикой → конфликт от агента (флаг `contested`) → вердикт → на 1 октября срок 14.11 (v2, superseded), на 1 ноября 28.11 (v3, active).

### M2. Вход + MCP — готов (без проверки на настоящих ChatGPT и Claude)

- **Сервер авторизации** (`frood-auth`): метаданные AS (RFC 8414, с `client_id_metadata_document_supported`, `authorization_response_iss_parameter_supported`) и защищённых ресурсов `/v1` и `/mcp` (RFC 9728); `/oauth/authorize` → выбор провайдера → вход → согласие → код; `/oauth/token` (код + PKCE S256, refresh с ротацией; повтор refresh или кода отзывает всю семью токенов); `/oauth/register` (DCR); `/oauth/revoke` (RFC 7009). Клиенты — CIMD (документ по `https://` client_id, защита от SSRF, кэш) или DCR.
- **Вход людей** — только через внешнего OIDC-провайдера (Google, Entra, корпоративный SSO): discovery, PKCE, проверка ID-токена по JWKS, nonce, `email_verified`; пускаются адреса из `auth.allow` / `auth.allow_domains`. Провайдер `dev` (ввести email) разрешён только на loopback без `public_url`. Сессия — cookie `frood_session` (HttpOnly, SameSite=Lax, Path=/oauth, Secure при https); POST-формы проверяют Origin.
- **Согласие:** по умолчанию read + capture + propose; `decide` никогда не отмечен заранее; `admin` предлагается, только если клиент его запросил.
- **API:** каждый маршрут `/v1` требует Bearer-токен с нужным scope; 401 и 403 несут `WWW-Authenticate` со ссылкой на метаданные ресурса. Токен, выданный для `/mcp`, на `/v1` не принимается. Новые маршруты: `/v1/me`, `/v1/tokens` (личные токены). Заголовок `Frood-Actor` удалён.
- **MCP** (`frood-mcp`, rmcp 3.5): Streamable HTTP без сессий, JSON-ответы, защита от DNS-rebinding по хосту issuer; 10 инструментов из docs/12 §4, список фильтруется по scopes токена (без `decide` нет `submit_verdict`); инструкции сервера для модели.
- **CLI:** `frood token create | list | revoke` — личные токены для скриптов и ботов (первый токен инсталляции).

**Проверено:**
- 48 тестов: сквозной OAuth-поток с моковым OIDC-провайдером (Ed25519-ключ генерируется в тесте) — discovery по 401, DCR, отказ на чужом redirect URI, вход, согласие, неверный PKCE, обмен кода, аудитория токена, MCP `initialize` / `tools/list` / `capture_note` / `propose_change` / `list_inbox` / отказ `submit_verdict`, ротация refresh, отзыв семьи при повторе, одноразовость кода; отказ человеку вне allowlist; токены и scopes на `/v1`. clippy `-D warnings`, rustfmt.
- Вживую на собранном бинарнике: 401 с `WWW-Authenticate` на `/mcp`, метаданные, `frood token create`, MCP через curl, `/v1/me`; `/oauth/authorize` с настоящим client_id Claude (`https://claude.ai/oauth/mcp-oauth-client-metadata`) — документ скачан с claude.ai, redirect `https://claude.ai/api/mcp/auth_callback` принят.

- Первый вход автора из Claude Code упал: «Cross-site request refused». Причина — `<meta name="referrer" content="no-referrer">` на страницах входа: с ним браузер шлёт `Origin: null` в POST-формах, а сервер проверяет Origin. Тесты этого не ловили, потому что ставили заголовок сами. Исправлено на `same-origin`; весь поток пройден в настоящем браузере (вход → согласие → код → токен → MCP).

- **Claude Code автора подключён к локальному Frood** (`~/frood-local`): зарегистрировался через CIMD (`https://claude.ai/oauth/claude-code-client-metadata`), вход, согласие, токены с аудиторией `/mcp`. Нашлась вторая ошибка: Claude Code запрашивает все scopes из метаданных ресурса, а страница согласия заранее отмечала всё запрошенное, кроме `decide`, — клиент получил `admin` и `journal:read`. Теперь заранее отмечены только read, capture, propose, а `/mcp` объявляет только нужные инструментам scopes. Выданный до исправления токен безвреден: он привязан к `/mcp`, где эти права не используются.

**Не проверено:** настоящие ChatGPT и Claude в облаке (нужны публичный HTTPS и OIDC-клиент, см. ниже).

### Что нужно для проверки с ChatGPT и Claude (пункт 5)

Claude и ChatGPT подключаются к MCP-серверу **из своего облака**, а не с компьютера автора, и человек при подключении входит в Frood через браузер. Поэтому:

1. **Публичный адрес по HTTPS** — домен (например, `mem.example.com`), направленный на VPS, где запущен Frood за обратным прокси с сертификатом (Caddy получает его сам). Адрес `127.0.0.1` из облака Anthropic или OpenAI не виден.
2. **OAuth-клиент у провайдера входа**, чтобы Frood мог спросить у Google (или корпоративного SSO), кто входит: в Google Cloud Console → APIs & Services → Credentials → OAuth client ID (Web application), redirect URI `https://<домен>/oauth/callback/google`. Получаются client_id и client_secret, они идут в `frood.yaml` (`auth.providers`) и в `.frood/secrets.env`.

Claude Code и другие локальные клиенты ничего из этого не требуют: Frood на `127.0.0.1` с провайдером `dev` или личный токен.


## 18 октября 2026, день: M3

### M3. Ввод и извлечение — готов (без живой проверки с настоящими моделями)

План — [19_m3_plan.md](19_m3_plan.md). Что работает:

- **Захват** `POST /v1/capture`: текст (JSON) или файл (multipart: голосовое, аудио, документ до 25 МБ). Отвечает сразу; `GET /v1/sources/{id}/status` показывает запуски и созданные предложения.
- **Dispatcher и очередь** (`frood-dispatch`): читает журнал со своим checkpoint, по правилам джоб ставит запуски (один на джобу и событие), исполняет с повторами и растущей задержкой; после перезапуска сервера прерванные запуски возвращаются в очередь.
- **Стандартные джобы** (меняются и выключаются в `jobs:`):
  - `transcribe`: медиа → текст источника через модуль `media.transcribe`;
  - `extract`: текст → наблюдения → сущности → похожие утверждения → предложения. Ответ модели сохраняется в запуске до применения, поэтому повтор не платит за второй вызов и не плодит дублей. Цитата каждого изменения становится доказательством с точным диапазоном символов;
  - `embed`: эмбеддинги нового знания.
- **LLM gateway** (`frood-llm`, встроенный модуль): `llm.complete` со структурированным ответом через Anthropic (серверный fallback при отказе для моделей, которые его принимают) и OpenAI (strict JSON schema); `llm.embed` через OpenAI. Моделей по умолчанию нет — модель всегда указывается в конфиге (D4, раунд 12). Отказ модели, обрезанный ответ и временные ошибки различаются.
- **Поиск**: Postgres FTS + pgvector, слияние по рангу; без аккаунта эмбеддингов — только слова. `GET /v1/search`, MCP `search_knowledge`.
- **Хост модулей** (`frood-modhost`): протокол `GET /manifest`, `GET /healthz`, `POST /v1/capabilities/{capability}`, сервисный токен в обе стороны. `frood apply` кладёт токен модуля в секреты, пишет модулю отдельный env-файл только с его секретами и поднимает его в Compose; ядро находит модуль и регистрирует токен со scopes из манифеста.
- **Модули** (Apache-2.0): `stt-openai` (модель в `config.model`; OGG/Opus из Telegram конвертируется ffmpeg) и `telegram` (long polling — публичный адрес не нужен; `/link <код>`; текст, голос, файлы; ответ «сохранено» потом превращается в итог: что запомнено, что ждёт решения; en/ru).
- **Связка каналов**: `frood link telegram --email …` или `POST /v1/channels/telegram/link-codes` (scope `admin`, как личные токены) выдают одноразовый код на 15 минут; модуль погашает его и дальше пишет как `user:<id>/via/telegram`.

**Чьё это действие (по R1′):** из заметки, которую человек отправил сам, `extract` предлагает от его имени (`user:<id>/via/extract`) — новые факты без конфликта принимаются сами; изменения и конфликты ждут вердикта. Из источников, захваченных не человеком, — `agent:extract`, всё на ревью.

**Проверено:**
- 76 тестов ядра и 7 тестов модулей; clippy `-D warnings`; CI зелёный (ядро, образ, оба модуля с образами).
- Сквозной тест конвейера с записанными ответами провайдеров: заметка «Договорились с Олей: релиз 2.4 — 14 ноября» → принятое обязательство, срок 14.11, новая сущность «Оля» — и субъект, и владелец; английский запрос «release deadline in November» находит его по смыслу; Telegram-аккаунт связывается кодом, чужой аккаунт получает отказ; голосовое → распознавание → извлечение → конфликтное предложение, утверждение помечено `contested`.

- Локальный Frood автора обновлён до M3, данные на месте.

### M4. Задачи и агенты — готов (без живой проверки с настоящим Claude Code)

План — [21_m4_plan.md](21_m4_plan.md). Что работает:

- **Джобы-агенты** `uses: agents.execute`: рантайм, агент, модель, аккаунт и `budget.max_usd` называются в конфиге всегда (A3, по аналогии с D4); без них джоба выключена с понятным предупреждением. Инструкции — текстом или путём к файлу; права — только чтение, заметки, предложения, журнал.
- **Запуск агента**: ядро выдаёт запуску свой токен (`frood_run_…`; права джобы ∩ разрешённые агентам, никогда `decide`; пишет как `agent:<джоба>` или `agent:<джоба>/for/<человек>`), передаёт рантайму MCP-серверы (Frood + источник запуска) и учётные данные, следит за запуском: события, стоимость, бюджет, конец. При любом завершении рантайм получает `stop` и освобождает сессию; токен отзывается, открытые вопросы закрываются; в журнал пишутся `run.*` и `question.*`.
- **Вопросы и продолжение**: `ask_user` (MCP, только токену запуска) кладёт вопрос в `GET /v1/questions`; когда агент закончил ход, запуск ждёт (`waiting_for_input`). Ответ через `POST /v1/questions/{id}/answer` или MCP `answer_question` (только человеку) — и запуск продолжается в той же сессии с новым токеном. Срок ожидания и `on_expire: skip | cancel | default_answer`. Ответы доходят до агента ровно один раз.
- **Сообщения на ходу**: `POST /v1/runs/{id}/messages` — рантайм доставляет сразу, если умеет; иначе агент продолжает сессию с сообщением, как только закончит ход.
- **Расписания**: `on: [{ schedule: "0 3 * * *", timezone: Europe/Amsterdam, for_each: source }]`. Тик — событие журнала `schedule.tick`, dispatcher превращает его в запуск как любое событие. Часовой пояс обязателен; переход на летнее время учитывается. Расписание считает с момента, когда сервер его впервые увидел; пропущенные за простой тики выпускаются один раз (с числом пропущенных). Тик захватывается в той же транзакции, что и записывается, — два сервера не выпустят его дважды.
- **Источники** `sources:` (`uses: mcp`): адрес MCP-сервера, заголовки с секретами, `scope`, `authoritative`. Инструмент `source:${source}` разворачивается в источник запуска; агент получает сервер `source-<имя>` и в первом сообщении — источник, его scope и «с какого момента читать» (checkpoint на пару джоба+источник сдвигается, когда запуск успешен).
- **`daily-sweep`** из стандартного набора: встроенные инструкции и инструменты; включается, когда в конфиге названы расписание, рантайм, агент, модель, аккаунт и бюджет.
- **Авто-принятие (W4′)**: джоба с `auto_accept: { when: authoritative_source }` — политика `authoritative-source` принимает новое и изменения агента, если запуск читает ровно один источник с `authoritative: true`; конфликты всегда ждут человека.
- **Аккаунты-подписки** `kind: subscription` (`owner`, токен `claude setup-token` или `auth.json` Codex): только джобы-агенты, только агент вендора (`claude-code` / `codex`), только запуски от имени владельца — проверяется и в конфиге, и при старте; в шлюз моделей подписка не попадает (A4).
- **Бюджеты**: на запуск (`max_usd`, `max_minutes`) и на аккаунт в месяц (`budget.monthly_usd`, по тому, что сообщают агенты). Превышение — остановка; новые запуски сверх месячного бюджета не стартуют.
- **Контракты** в `contracts/`: `agents.execute@1` и `media.transcribe@1` — описание и JSON Schema.
- **Модуль `runtime-docker`** (Apache-2.0): каждый ход агента — новый контейнер из образа агента (без capabilities, без новых привилегий, read-only корень, лимиты CPU/памяти/процессов), домашняя папка — том запуска, где Claude Code и Codex хранят сессию. Claude Code: только MCP-серверы запуска (`--strict-mcp-config`), без встроенных инструментов, `dontAsk` с разрешёнными серверами, сессия = id запуска, остаток бюджета — `--max-budget-usd`. Codex: серверы через `-c`, продолжение по thread id. Образы `agent-claude-code` (2.1.302), `agent-codex` (0.163.0) и `agent-fake` — подделка без вызова моделей. У модуля в конфиге `host_docker: true` (сокет Docker = root на машине, A2); `frood plan` об этом говорит.

### Вложения (Y1), шаг 1: выпуск 0.1.7 вместе с хранилищем и подключениями (25.10)

- **Модель:** вложение — источник Frood со своим файлом или адресом, привязанный к знанию (таблица `attachments`, миграция 0011), а не к версии: новые версии его сохраняют. К изменению, которое ждёт решения, вложение привязывается до решения; при принятии переходит к знанию, которое изменение создало или поменяло. Снять вложение можно, источник остаётся. Источник вложения не читает извлечение (он поясняет знание, а не несёт новое); видео и аудио расшифровываются, как голосовые.
- **API:** `GET`/`POST /v1/assertions/{id}/attachments` и `/v1/proposals/{id}/attachments` — файл (multipart, с подписью в `text`) или ссылка (`uri`, `title`); `DELETE /v1/attachments/{id}`; `GET /v1/sources/{id}/file` — картинки, видео и звук открываются на месте, всё остальное скачивается, поэтому загруженная страница не выполнится в консоли. У ссылки без названия сервер сам берёт заголовок страницы (`og:title` или `<title>`): только публичные адреса, до 256 КБ, до трёх перенаправлений. В Inbox у изменения — его вложения и вложения знания, которое оно меняет. Канал находит запись по своему сообщению: `GET /v1/channels/{channel}/messages/{ref}`.
- **Консоль:** раздел «Вложения» в подробностях знания и записи Inbox: «Прикрепить», перетаскивание, вставка файла или ссылки; превью фото (по нажатию — крупно), плеер видео и аудио, карточка ссылки с доменом, скачивание документов; в строке Inbox — скрепка с числом. В «Записать заметку» можно приложить файл; в подробностях записи — превью её файла.
- **Бот:** фото и видео с подписью — заметка, как голосовые. Фото, видео, файл или ссылка в ответ на карточку прикрепляются к ней (запись бот узнаёт по кнопкам карточки, а у решённой — спрашивает Frood), бот отвечает «📎 Прикрепил к «…»». На карточке — «📎 2 — названия».

### Вложения (Y1), шаг 2: хранилище файлов (25.10)

- **Конфиг:** `storage.objects` — `disk` (по умолчанию: папка `.frood/objects` рядом с `frood.yaml`, или своя `path`), `s3` (любое S3-совместимое: AWS, B2, R2, SeaweedFS, MinIO — `endpoint`, `bucket`, `region`, `prefix`, ключи, `path_style`) или `database` (как раньше, в Postgres). `max_mb` — самый большой файл: по умолчанию 100 МБ, в базе — 25. Консоль узнаёт предел из `/v1/version`.
- **Как лежат:** ключ файла — его SHA-256, одинаковый файл хранится один раз; в папке — `ab/abcd…`, запись через временный файл. S3 — подпись AWS Signature V4 без сторонних библиотек; проверена тестом по примеру из документации AWS и вживую на SeaweedFS (запись, чтение, 404, 403 на чужой ключ). В таблице `blobs` у файла в хранилище нет байтов (миграция 0012), читается он из хранилища.
- **Переезд:** при запуске сервер переносит файлы, лежавшие в базе, в хранилище — по 20 за раз, в фоне.
- **Деплой:** `frood apply` создаёт папку с меткой `.frood-objects`, монтирует её в контейнер сервера (`/var/lib/frood/objects`) и только для чтения — в модуль бэкапа (`/frood/objects`); запущенный от root отдаёт её пользователю 10001, от имени которого работают сервер и модуль. Без метки сервер в контейнере держит файлы в базе и пишет почему: папка, которую никто не смонтировал, пропала бы вместе с контейнером.
- **Бэкап:** `backup.target@1` получил `objects.path`: папка файлов идёт в тот же снимок restic (без меток и недописанных файлов), `manifest.json` считает её файлы, проверка восстановления сверяет их число по снимку. `frood restore` восстанавливает весь снимок и кладёт файлы туда, где их держит восстановленный `frood.yaml`. S3 бэкап не берёт: за ним следит само хранилище (версии). Экспорт берёт файлы из хранилища и выгружает вложения.
- Проверка: тесты хранилища (папка, подпись, адреса), журнала знаний (переезд из базы в папку, предел размера), API (вложения ложатся в папку), Compose (папка у сервера и у модуля бэкапа, не у остальных), модуля бэкапа (подсчёт файлов); сквозной тест бэкапа в Docker (`deploy/e2e/backup-restore.sh`) теперь прикрепляет фото и проверяет, что после удаления и `frood restore` файл вернулся и экспорт совпал; 13 сценариев консоли.

### Подключения из консоли (Y3), шаг 1: источники с токеном (25.10)

- **Второй слой конфига.** Источники, подключённые в консоли, лежат в базе (`config_overlay`, миграция 0013): каждое изменение — новая ревизия с тем, кто и когда. Источник из `frood.yaml` главнее: консоль показывает его с пометкой «из frood.yaml» и не даёт менять. Новый источник читает ближайший проход (`for_each: source`) без перезапуска сервера.
- **Токены** хранятся в базе запечатанными (age) ключом `FROOD_VAULT_KEY` из файла секретов: `frood init` создаёт его, `frood apply` добавляет в старые установки. Ключ попадает в бэкап вместе с остальными секретами (зашифрованными ключом восстановления). В слое конфига и в ответах API токена нет — только ссылка `${vault:…}`; агенту он подставляется при запуске.
- **API** (нужен `admin`, как для `frood apply`): `GET /v1/connections`, `POST /v1/connections/check` — подключиться к MCP-серверу и перечислить инструменты (с пометкой, какие только читают), `PUT`/`DELETE /v1/connections/{name}`. Проверку делает свой маленький MCP-клиент (Streamable HTTP, ответы JSON или поток событий); ошибки говорят, что исправить: адрес, токен, сервер.
- **Консоль:** «Источники → Подключено → Подключить источник» — каталог (YouTrack, GitHub, Linear с токеном; Jira, Confluence, Notion, GitLab, Slack, Google Drive — пометка «OAuth», вход появится следующим шагом; «Любой MCP-сервер»), форма: адрес, токен со ссылкой «где взять», «Проверить», инструменты с отмеченными читающими, «что там читать», «решения отсюда можно принимать без меня» (`authoritative`). У подключённого — правка без повторного ввода токена и «Отключить».
- **`frood config export`** печатает источники из консоли строками `frood.yaml` для git; токены — ссылками `${secret:SOURCE_<NAME>_TOKEN}`, их значения не выводятся. Экспорт знаний берёт слой конфига без токенов.

### Подключения из консоли (Y3), шаг 2: вход через OAuth (25.10)

- **Как по спецификации MCP (2025-06-18):** сервер отвечает 401 и называет свои метаданные (RFC 9728) или они лежат по известному адресу; оттуда — сервер авторизации и его адреса (RFC 8414 или OpenID); Frood регистрируется у него сам (RFC 7591, клиент без секрета), человек входит на странице сервиса с PKCE (S256) и `resource`, возвращается на `…/v1/connections/signed-in`, код меняется на токены. Начатый вход живёт полчаса, его данные запечатаны в базе (`oauth_pending`, миграция 0014).
- **Токены** запечатаны в сейфе. В заголовке источника — ссылка `${oauth:…}`: токен подставляется при каждом использовании (запуск агента, проверка), а истекающий (меньше минуты до конца) сначала обновляется через refresh token и снова запечатывается.
- **Безопасно по умолчанию:** источник после входа подключён без инструментов. Консоль сама открывает его, проверяет сервер и отмечает читающие инструменты; человек сохраняет выбор.
- **Консоль:** у нового подключения рядом с «Проверить» — «Войти» (основная кнопка для сервисов с OAuth в каталоге); после возврата — «Вход выполнен: …» и форма источника. Если сервер не даёт регистрироваться или не говорит, где входить, ошибка советует подключить его токеном.

### Подключения из консоли (Y3), шаг 3: джобы и расписания (25.10)

- **Что меняется из консоли:** у любой стандартной джобы — включена или нет, когда запускается (расписания cron с часовым поясом; «каждый день в», «по будням в», «каждые N часов» или своё выражение), модель, кто платит (из аккаунтов конфига) и пределы одного запуска агента. Остальное (агент, рантайм, инструкции, права) — в `frood.yaml`. Джоба, которую меняет `frood.yaml`, в консоли с пометкой «из frood.yaml» и только для чтения; джобы, которые запускаются от событий (извлечение, распознавание, индекс), расписания не получают.

Перед сохранением конфиг с изменением проверяется теми же правилами, что `frood.yaml` (`frood_config::check`); диспетчер собирает джобы заново, и ближайшая минута расписаний уже идёт по новому — без перезапуска. Ответ говорит, если джоба сохранена, но не работает (например, ночному проходу нужен агент из `frood.yaml`).
- **Консоль, «Автоматизации»:** видны все джобы, неработающие — пунктиром с «Не работает» и причиной; у каждой — шестерёнка «Настроить»; у изменённых — пометка «изменено здесь» и «Вернуть как было».

### M9, шаг 1: свои правки без ревью и находки агентов «не проверено» (25.10)

Раунд 23 принят: F1, F2, F4, F5, QF1 — (а), QF2 — (а), QF3 — (б). F3 переделан по замечанию «не надо пачку шаблонов»: значения по умолчанию встроены в сервер, шаблонов и бандлов нет ([27](27_m9_first_hour.md)).

- **Свои правки (F4).** Политика `own-change` принимает изменение знания, которое целиком принадлежит автору: все его версии предложил этот человек (заметкой, импортом, правкой), все свидетельства — из его источников, и на знании нет конфликта. «Перешли на Postgres 17» при своём «Postgres 16» больше не ждёт. Знание от агента, коллеги или подключённого источника меняется, как раньше, через решение.
- **Находки агентов (QF3).** Политика `agent-finding`: новое знание, которое агент нашёл в обычном (не доверенном) источнике, принимается сразу и получает пометку `needs_verification` с причиной («found by agent:daily-sweep; not verified»). Изменения, конфликты и слияния от агентов ждут человека. Доверенный источник по-прежнему принимается без пометки (`authoritative-source`).
- **Пометка видна везде.** В версиях знания есть поле `unverified`, поэтому оно попадает в списки, поиск, «Сейчас» и ответы MCP. Инструкция MCP-сервера просит ассистента говорить «не проверено». Консоль показывает пунктирную плашку «не проверено», а в подробностях — кнопку «Верно» (`POST /v1/assertions/{id}/verify`: проверка человеком, политика `own-check`, пометка снимается). Бот пишет «не проверено» в `/now` и в ответах на вопросы.
- **Настройки:** `policies.auto_accept_own_changes` и `policies.accept_agent_findings` (по умолчанию включены).
- **Проверка:**
  - тесты политик;
  - тест журнала знаний: своя замена принята, находка агента помечена, своя замена чужого ждёт, «Верно» снимает пометку, замена от агента ждёт;
  - API-тест агента: новое знание принято с пометкой, изменение ждёт, агент не может его решить;
  - тест бота;
  - 17 сценариев консоли.
  - Старые тесты, которым нужно было «ждущее» предложение от агента или человека, запускаются с выключенными новыми правилами — так же, как демо-установка консоли.
