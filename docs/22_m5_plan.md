# M5. Inbox и уведомления — план реализации

> Этап M5 из [17_mvp_plan.md](17_mvp_plan.md): записи Inbox, маршрутизация, Telegram — уведомления с кнопками и обновление сообщений, «исследовать перед обращением», сводка, напоминания по срокам. Результат — шаги 3–5 сценария: конфликт от ночного агента → запись Inbox → сообщение в Telegram с кнопками → перезапуск сервера ничего не теряет → вердикт кнопкой меняет знание, история видна в любом клиенте.
> Основание: фаза 5 ([15_inbox_attention.md](15_inbox_attention.md), N1–N8, N9′; QN1 — кнопки сразу ставят вердикт), R1′ (действие из канала — действие человека: `user:<id>/via/telegram`), M4 (вопросы агентов, запуски, расписания).

## 1. Как это работает

```
событие журнала (proposal.opened, question.asked, run.failed, напоминание по сроку, …)
   ─▶ ядро заводит запись Inbox — одну на ситуацию — или обновляет её
   ─▶ маршрутизатор: кому, насколько срочно (сейчас / в сводку / тихо), в какой канал
   ─▶ [исследовать перед обращением: запуск investigate, ждём не дольше max_wait]
   ─▶ notify.send@1 в канал человека: текст, ссылки на знание, кнопки
   ─▶ кнопка ─▶ модуль канала вызывает API от имени связанного человека: вердикт, ответ, отложить
   ─▶ ситуация разрешена (где угодно) ─▶ запись закрывается сама ─▶ notify.update@1 во всех каналах, где она показана
```

## 2. Что строим

| Часть | Где | Что |
|---|---|---|
| Записи Inbox | ядро | Вид (`proposal`, `question`, `reminder`, `alert`, `digest`), ситуация (предложение, вопрос, запуск, утверждение), почему появилась, срочность, кому, состояние `new → seen → snoozed / resolved`. Заводятся и закрываются по событиям журнала: вердикт, ответ, отмена, успешный повтор. Переживают перезапуск — это строки в базе, а не память процесса |
| API | ядро | `GET /v1/inbox` (свои записи, по важности), `POST /v1/inbox/{id}/seen`, `/snooze`, `/act` — действие по записи: вердикт, ответ, отложить, «выполнено»; MCP `list_inbox` отдаёт записи Inbox, а не только предложения |
| Маршрутизатор | ядро | Кому, срочность и канал по правилам; тихие часы и лимит push — в конфиге `attention:` (B1, B2) |
| Доставка | ядро | Что, куда и каким сообщением показано; одно сообщение на запись и канал; повтор напоминаний с растущим интервалом; `notify.update` при разрешении |
| Контракты | `contracts/` | `notify.send@1`, `notify.update@1`; ответы приходят обратно через `POST /v1/inbox/{id}/act` от модуля с `channels:act` |
| Telegram | модуль | Сообщение по записи: что случилось, было и стало, цитата-доказательство, ссылки; кнопки — «Принять», «Отклонить», «Отложить», варианты конфликта, варианты ответа на вопрос агента; правка сообщения, когда ситуация решена где-то ещё; «что нового?» — сводка |
| Исследовать перед обращением | ядро + джоба `investigate` | Правило `attention.before_notify` (например, для конфликтов): запись ждёт итога агента не дольше `max_wait`, итог идёт в сообщение как контекст. `investigate` — агент, как `daily-sweep`: выключен, пока в конфиге не названы рантайм, агент, модель, аккаунт и бюджет (A3, A5) |
| Сводка | ядро + джоба `digest` | Личный checkpoint «просмотрено до»; что принято, что ждёт решения, ближайшие сроки, итоги и сбои фоновых запусков; по расписанию из конфига или по запросу; без модели (B3) |
| Напоминания | ядро + планировщик | Из `commitment` со сроком `due` (B4), из давних `open_question`; кнопки «Выполнено» (закрыть утверждение от вашего имени) и «Перенести» |
| Тревоги | ядро | Упавший запуск, превышенный бюджет, недоступный модуль → `alert` с кнопкой «Повторить» |

## 3. Проверка

- Сквозной тест шагов 3–5 с поддельным агентом и поддельным Telegram Bot API: конфликт → запись → сообщение с кнопками → перезапуск ядра → нажатие кнопки → старая версия `superseded`, новая `active`, сообщение поправлено, запись закрыта.
- Вживую на боте автора: конфликт из `daily-sweep` (подписка) → сообщение → вердикт кнопкой.
