# Frood за общим прокси — предложение

> Статус: принято (раунд 25): V1, V2; QV1 — (а), QV2 — (а). Сделано: `deploy.proxy.external` во Frood, репозиторий `vps-gateway`. Дальше — выпуск и переезд сервера.
> Основание: просьба автора 26.10 — сервер не должен зависеть от Frood; Frood — один из проектов на нём, а не главный.

## 0. Как сейчас

Когда задан `server.public_url`, `frood apply` поднимает Caddy: он держит 80/443 и сертификаты, а его Caddyfile Frood переписывает целиком при каждом применении. Другие приложения на том же сервере живут у Frood в гостях: `deploy.proxy.routes` — один файл маршрутов внутри сайта Frood, только под путями и без своих доменов.

Если Frood упал, его переустанавливают или `frood apply` ошибся, перестают открываться и все соседи.

## 1. Как предлагаю

**Прокси принадлежит серверу.** Отдельный Caddy, вне любого проекта: у каждого проекта в нём свой файл. Проект на своём домене кладёт блок сайта, проект под путём на общем домене — маршруты для этого пути. Файл проекта подхватывается сам. Если файл сломан, Caddy оставляет прежний конфиг, остальные сайты работают.

Готовое решение здесь — сам Caddy. Своё — только раскладка папок, установщик и подхват файлов. Это отдельный репозиторий, не Frood.

**Frood умеет жить за чужим прокси** (новое в Frood):

```yaml
deploy:
  proxy:
    external: /srv/edge/paths/frood.caddy   # свой Caddy не запускать; писать только свои маршруты
```

- Свой Caddy Frood не запускает. Сервер слушает `127.0.0.1:8080`, как и сейчас.
- При `frood apply` Frood пишет в указанный файл только свои маршруты: путь Frood и адреса `/.well-known/…` в корне домена (для OAuth их ищут именно там). С отдельным доменом это блок сайта целиком.
- Чужие файлы Frood не трогает и прокси не перезапускает: подхват — дело прокси.
- Без `external` всё как сейчас: на пустом сервере Frood приносит свой Caddy. Новому человеку общий прокси не нужен.
- `deploy.proxy.routes` остаётся для тех, у кого Frood — единственный хозяин.

## 2. Что ещё смотрел

- **Traefik** с метками Docker и файловым провайдером — стандарт для многих контейнеров на одном сервере. Сложнее в настройке. Сервисы вне Docker (systemd) всё равно описываются файлами. Выигрыша против Caddy с файлами здесь нет.
- **caddy-docker-proxy** — Caddy, который строит конфиг из меток контейнеров. Ему нужен доступ к сокету Docker, а это права root. Сервисы вне Docker — снова файлом.
- **Coolify, Dokploy, CapRover** — платформы, которые сами разворачивают проекты. Они становятся новым «рулевым» и хотят управлять Compose каждого проекта, в том числе Frood. Это обратное тому, что нужно.
- **Nginx Proxy Manager** — настройки в своей базе через веб-интерфейс, не файлами в git.

## 3. Порядок

1. Репозиторий общего прокси: раскладка, установщик, подхват файлов, файлы соседей.
2. Frood: `deploy.proxy.external`, тесты, выпуск.
3. Переезд сервера:
   - общий прокси готов, но не запущен;
   - `frood apply` с `external` — Caddy Frood уходит;
   - общий прокси сразу занимает 80/443;
   - сертификаты можно перенести из тома Caddy Frood, чтобы не выпускать заново.

   Простой — секунды. Если что-то не так, откат — прежний `frood.yaml` и `frood apply`.

## 4. Решения (раунд 25, 26.10)

- **V1 — ok:** общий прокси — отдельный приватный репозиторий `vps-gateway` на GitHub автора (QV2 — а).
- **QV1 — (а):** Caddy из официального репозитория пакетов как служба systemd, без Docker.
- **V2 — ok:** `deploy.proxy.external` во Frood, затем переезд сервера (каждое действие на сервере — с разрешения автора).
