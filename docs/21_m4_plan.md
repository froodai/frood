# M4. Задачи и агенты — план реализации

> Этап M4 из [17_mvp_plan.md](17_mvp_plan.md): расписания, джобы-агенты, запуски с ожиданием ответа, рантайм «контейнеры на VPS» (Claude Code, Codex), ask_user и сообщения на ходу, аккаунты и бюджеты, `daily-sweep` по MCP-источнику. Результат — шаг 3 сценария без уведомления: ночной агент находит в источнике «релиз переносим на 28.11» и открывает конфликтное предложение.
> Основание: фаза 3 ([13_work_agents.md](13_work_agents.md), W1′–W9), фаза 4 (источники как возможности модулей, I4′), R1′ (агент на расписании пишет как `agent:<джоба>`), D4 (моделей по умолчанию нет). Dispatcher и очередь по событиям уже сделаны в M3.

## 1. Как работает запуск агента

```
schedule.tick / событие / POST /v1/runs ─▶ dispatcher ─▶ run (queued)
   ─▶ ядро выпускает токен запуска (права джобы, audience /mcp, живёт до конца запуска)
   ─▶ agents.execute@1.start(spec) у модуля рантайма ─▶ контейнер с Claude Code или Codex
        агент работает через MCP Frood: search, get_context, propose_change, ask_user, report_progress
   ─▶ ask_user: вопрос в Inbox, запуск waiting_for_input, контейнер завершается
   ─▶ ответ (API, MCP answer_question, позже Telegram) ─▶ resume(run, session, ответ) — та же сессия
   ─▶ итог: отчёт, предложения, стоимость; бюджет превышен — stop
```

## 2. Что строим

| Часть | Где | Что |
|---|---|---|
| Расписания | `frood-dispatch` | Триггер `{ schedule: "0 3 * * *", timezone, for_each: source }`; тик — событие журнала `schedule.tick`; пропущенный тик выпускается один раз после старта |
| Джобы любого вида | `frood-config`, `frood-dispatch` | Кроме стандартных — свои джобы: `uses: agents.execute` с инструкциями, инструментами (MCP), рантаймом, агентом, моделью, аккаунтом, правами, `ask_user`, бюджетом; `llm.complete` с инструкциями |
| Запуски | `frood-dispatch`, API | Состояние `waiting_for_input`; журнал шагов (`run_events`): вызовы инструментов, токены, стоимость. `GET /v1/runs`, `POST /v1/runs` (ручной), `POST /v1/runs/{id}/messages`, `POST /v1/runs/{id}/cancel` |
| Токен запуска | `frood-auth` | Права = права джобы ∩ разрешённые агентам (read, capture, propose; никогда decide); действует до конца запуска; пишет как `agent:<джоба>` |
| Вопросы | ядро, API, MCP | Таблица вопросов; `GET /v1/questions`, `POST /v1/questions/{id}/answer`; MCP: `ask_user`, `report_progress` (только токену запуска), `list_questions`, `answer_question` (людям); срок ожидания и `on_expire: skip / cancel / default_answer` |
| Контракт рантайма | `contracts/`, `frood-modhost` | `agents.execute@1`: capabilities, start, send, resume, cancel_turn, stop, status, events |
| Рантайм «Docker на VPS» | `modules/runtime-docker` (Apache-2.0) | Контейнер на запуск: образы `agent-claude-code` и `agent-codex`; MCP-конфиг (Frood с токеном запуска + MCP-источники); рабочая папка в томе на запуск, чтобы продолжить сессию после ответа |
| Аккаунты и бюджеты | `frood-config`, `frood-dispatch` | Вид `subscription` (подписка одного человека, только его запуски, через CLI вендора); бюджеты на джобу (`max_usd`, `max_minutes`) и на аккаунт в месяц; превышение — остановка запуска |
| Источники | встроенный модуль `mcp` | Секция `sources:` — MCP-сервер как источник (адрес, заголовки с секретами, область, `authoritative`); агент получает его как инструмент `source:<имя>`; checkpoint источника для «изменений с прошлого раза» |
| `daily-sweep` | стандартный набор | Агент проходит источник с прошлого checkpoint, сверяет с памятью, предлагает новое, замены и конфликты с цитатами; от имени `agent:daily-sweep` — всё на ревью; авто-принятие только для `authoritative` без конфликта (W4′) |

## 3. Проверка

- Модуль рантайма с поддельным агентом (скрипт вместо модели): запуск по расписанию, вопрос, ответ, продолжение той же сессии, сообщение на ходу, остановка по бюджету, токен запуска без права вердикта.
- Поддельный MCP-источник «командный чат» с сообщением о переносе релиза → `daily-sweep` → конфликтное предложение.
- Вживую с настоящим Claude Code — только с разрешения автора на траты (агент делает несколько вызовов модели).
