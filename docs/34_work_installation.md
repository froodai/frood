# M12. Рабочий Frood — предложение

> Статус: принято (раунд 29, 23.11): QW1, QW2, QW3, QW4, W1. W1 и W4 (один бот на две установки) сделаны, см. §4 и §5; выпуск 0.1.16, вживую не проверено. Источник Glean — §6, после 0.1.16, вживую не проверен.
> Основание: автор в Cockpit 23.11 — у него два пространства, личное и рабочее; корпоративные данные не должны лежать на личном VPS; рабочий Frood он хочет во внутренней Kubernetes-платформе компании со своим рабочим аккаунтом Google, а личный VPS оставить для личного. В замысле личная и рабочая установки уже раздельны: решение D9″ в [журнале решений](README.md#журнал-решений) — «пользователи без пространств и ролей, разделение инсталляциями».

## 0. Что вижу

**Внутренняя платформа компании.**
- Веб-консоль поверх Kubernetes, свой namespace (место в кластере) создаётся самим автором.
- Деплой — образ из реестра контейнеров и Helm-чарт через CI. Можно и `kubectl` со своей машины.

**Что подходит сразу.**
- Postgres: управляемая база, адрес и пароль приходят Secret'ом, бэкапы настраиваются на стороне платформы. Frood нужны расширения `vector`, `pg_trgm`, `btree_gist`; доступность каждого надо уточнить у администраторов платформы.
- Бакет с S3-совместимым доступом — для файлов и бэкапов.
- Ingress с TLS: внутренний адрес, доступный только из корпоративной сети и VPN, или публичный.
- Вход через рабочий аккаунт Google (OIDC) — Frood уже умеет.

**Что мешает.**
- **ИИ.** Рабочие данные не идут через личные подписки. Нужен корпоративный путь к модели: ключ API с оплатой компании или внутренний шлюз.
- **Агенты.** Сейчас Frood запускает агента в Docker-контейнере на своей машине, а в кластере Docker нет. Нужен рантайм для Kubernetes: каждый ход агента — отдельная задача (Job) в namespace автора.
- **Развёртывания в Kubernetes у Frood нет.** Нужны Helm-чарт и образы без root.
- **Чат.** Возможно, понадобится корпоративный чат вместо Telegram.
- Новый внутренний сервис, который читает рабочие системы, скорее всего проходит ревью безопасности.

**Заодно про личный VPS.** Проход по рабочему трекеру на VPS через подписку автора переедет в рабочий Frood. Выключим, как скажет автор.

## 3. Решения (раунд 29, 23.11)

- **QW1:** без VPN: публичный адрес, вход через Google, только рабочие аккаунты; Frood проверяет вход сам, прокси перед ним необязателен.
- **QW2:** корпоративный шлюз, совместимый с Anthropic API: адрес шлюза и ключ от команды-помощника; личная подписка не используется.
- **QW3:** Telegram, а не корпоративный чат. Бот один на обе установки: «тг бот один».
- **QW4 — (б):** обновления бота получает личный Frood. Рабочие он сразу передаёт рабочему Frood на его адрес с токеном и у себя не хранит. Рабочий Frood бота не опрашивает: он только отправляет сообщения тем же токеном бота.
- **Куда идёт сообщение** («почему он сам не может выбрать, куда слать»). Frood выбирает сам, спрашивает, только когда не уверен. По порядку:
  - ответ на сообщение бота идёт той установке, которая это сообщение прислала; у сообщений бота метка «Личное» или «Работа», кнопки несут установку в своих данных;
  - явная приставка в начале сообщения: «работа:» или «личное:»;
  - рабочие слова: рабочий Frood передаёт личному список номеров тикетов, проектов и имён коллег; список приходит хешами, сами слова на личном сервере не лежат;
  - обучение: автор поправил выбор — слова из сообщения попадают в список;
  - не уверен — бот спрашивает «Личное или Работа?» кнопками; до ответа сообщение лежит только в памяти, не на диске.
  - Чтобы выбрать, личный Frood не отправляет текст в LLM: рабочий текст не должен попадать в личную подписку.
- **Mini App:** одна кнопка в боте, в приложении переключатель «Личное / Работа»; обе установки проверяют подпись Telegram одним токеном.
- **W1 принято:** «делай доработки». Это рантайм агентов для Kubernetes, Helm-чарт и аккаунты с ключом API для задач агентов.

## 4. Как сделано / W1

### Модели через шлюз

**Аккаунт.** У аккаунта `kind: api_key` ключ задаётся одним из двух способов:
- `secret` — сам ключ;
- `api_key_helper` — команда, которая печатает ключ. Это для шлюзов, которые выдают короткоживущие ключи.

Задать оба способа или ни одного — ошибка конфига. Необязательный `base_url` — корень API шлюза без `/v1`. Это `https://…` или `http://` к адресу внутри установки: loopback, имя сервиса Compose без точек, имя Service в Kubernetes (`*.svc`, `*.svc.cluster.local`). Хост проверяется так, как его разбирает HTTP-клиент: `user:pass@`, обратная косая черта и имена вроде `127.0.0.1.example.com` проверку не обходят. Регистр букв не важен. Код — `frood-config`.

**Прямые вызовы ядра.** Сервер шлёт запросы на `base_url`. Команду `api_key_helper` он запускает через `sh -c`, ключ из её вывода держит пять минут, а после ответа 401 запускает команду ещё раз и повторяет запрос. Если 401 с одним ключом получили сразу несколько запросов, команда запускается один раз, остальные берут новый ключ. Если команда упала, в ошибку попадает её stderr, а stdout — нет: там может быть ключ. Код — `frood-llm`.

**Агенты.** Рантайм получает в `credentials` поле `base_url`, а также `api_key` или `api_key_helper`.
- Claude Code получает `ANTHROPIC_BASE_URL`. Ключ приходит в `ANTHROPIC_API_KEY` либо в настройку `apiKeyHelper` (`--settings`). Во втором случае Claude Code сам запускает команду внутри контейнера агента, поэтому команда должна быть и в образе сервера, и в образе агента.
- Codex получает `OPENAI_BASE_URL` с `/v1`. Аналога `apiKeyHelper` у Codex нет, поэтому `api_key_helper` для него отклоняют и валидация конфига, и рантайм.
- Подписке `base_url` не положен.

Код — общий `agents.rs` у runtime-docker и runtime-k8s. Контракт описан в `contracts/agents.execute/1`.

### runtime-k8s: агенты как задачи Kubernetes

**Ход агента.** Каждый ход — Job из одного пода, в namespace модуля или в `namespace`. Порядок шагов:
1. Job создаётся приостановленным (`suspend: true`).
2. Рядом создаётся Secret с env и аргументами хода. Его владелец — этот Job.
3. Job отпускают патчем `suspend: false`.

Ключ, промпт и токен запуска лежат только в Secret. В спецификации Job — ссылки `secretKeyRef` и аргументы вида `$(FROOD_ARG_n)`.

**Сессии.** Сессии запуска живут на отдельном PVC `frood-run-<run_id>`: это домашний каталог агента. Init-контейнер создаёт на нём рабочую папку. `stop` удаляет Job и PVC, Secret уходит вместе с Job. Ещё `stop` удаляет по метке все Job запуска: и те, о которых модуль забыл (он упал между созданием Job и записью запуска). Иначе приостановленный Job остался бы навсегда вместе с ключом в Secret.

**Под.**
- Пользователь 10001, `runAsNonRoot`, без повышения привилегий, все capabilities сброшены.
- Корневая файловая система только для чтения, `/tmp` — `emptyDir`.
- Seccomp `RuntimeDefault`, без токена API.
- `requests` равны лимитам.

Под проходит стандарт `restricted`.

**Время и отмена.**
- `activeDeadlineSeconds` равен `max_minutes` плюс минута: ход кончается, даже если `stop` не пришёл.
- Ядро, как и раньше, само шлёт `stop` по бюджету минут и при отмене.
- Job, который модуль не успел убрать (например, лежал), удалит TTL (`keep_finished_minutes`).
- Ход падает с понятной причиной, если: образ не скачивается, упал init-контейнер, под вытеснили, истёк срок, Job исчез.
- Если Job с именем хода уже есть (остался от попытки, о которой модуль забыл), модуль его удаляет и отвечает 503 с повтором. Следующая попытка начинается с чистого места.

**Права.** Только Role в своём namespace:

| Ресурс | Права |
|---|---|
| Jobs | create, get, patch, delete, deletecollection |
| Pods | list |
| pods/log | get |
| PVC | create, delete |
| Secrets | create |

Читать Secrets модуль не может. Под хода он находит списком по метке `job-name`, а не по имени: права `get` на поды у него нет.

**API.** Модуль ходит в API кластера по HTTPS с токеном своего ServiceAccount и перечитывает токен на каждый запрос. Watch нет: ядро опрашивает `status`.

**Где агент находит Frood.** Под агента находит Frood по `frood_url` — полному имени Service, например `http://frood.<namespace>.svc:8080`. Чарт задаёт его сам.

**Проверка.** Юнит-тесты гоняют модуль против API-сервера в памяти (`src/mock.rs`). Этот мок исполняет поддельного агента, проверяет правила `restricted` и умеет просроченный срок и отказ RBAC. Запросы вне Role он отклоняет, как настоящий API-сервер; тест сверяет эту Role с манифестом модуля и с Role в чарте. Тесты проходят:
- вопрос и возобновление в той же сессии;
- `stop`;
- падение и образ, который не скачивается;
- срок и отказ RBAC: 503 с повтором, том убран;
- ключ от команды-помощника: его нет ни в Job, ни в Secret;
- забытые Job запуска: повтор хода их убирает, `stop` удаляет их по метке.

### Helm-чарт `deploy/helm/frood`

**Сервер.**
- `frood.yaml` лежит в ConfigMap. Чарт сам дописывает `listen`, `public_url` (из ingress), `storage`, `deploy` и адреса модулей.
- Адрес базы берётся из готового Secret, остальные `${secret:…}` — из Secret через env.
- Токены модулей создаются один раз и сохраняются при обновлениях.
- Пробы: `/healthz` (startup и liveness) и `/readyz`.

**Файлы.** Три варианта:
- PVC — тогда одна реплика и `Recreate`;
- бакет S3;
- база.

**Вход.** По умолчанию публичный ingress, вход проверяет сам Frood (Google, `allow_domains`). Класс ingress, хост и issuer cert-manager задаются в values, поэтому так же ставится и только внутренний адрес.

Прокси входа перед консолью (external auth у ingress-nginx) включается отдельно. Пути `/mcp`, `/oauth`, `/.well-known` и `/v1` идут через второй Ingress без прокси: их клиенты носят токены Frood, а не браузерную сессию.

**Агенты.** runtime-k8s ставится со своими ServiceAccount, Role и RoleBinding. Агенты могут работать в другом namespace (`agents.jobNamespace`).

**Модули по желанию.**
- Telegram: одна реплика, `Recreate` — двое опрашивающих одного бота мешают друг другу.
- backup-restic: с PVC файлов он работает на узле сервера и читает файлы только для чтения.

**Сеть.** NetworkPolicy включается отдельно. Она открывает выход:
- в DNS;
- в интернет без частных диапазонов;
- к частным адресам из values (Postgres, шлюз);
- к подам релиза;
- модулю агентов — к API-серверу.

Входящие к модулям пускаются только от сервера, к подам агентов — ни от кого.

**Шлюз рядом.** Через `extraObjects` рядом можно поставить прокси шлюза: Deployment и Service. `base_url` указывает на имя этого Service. Пример `examples/llm-gateway.yaml` условный, без настоящего продукта.

**Образы.** Все образы теперь объявляют числового пользователя (`USER 10001`): иначе Kubernetes не может проверить `runAsNonRoot`. runtime-docker по-прежнему работает от root: ему нужен Docker хоста.

**Проверка.**
- `helm` на машине не установлен, поэтому `helm lint` и `helm template` локально не запускались. На ревью (helm 4.3.2) оба прошли: на примерах, на значениях по умолчанию и с каждой частью по отдельности (Telegram, бэкапы, NetworkPolicy, прокси входа, `extraObjects`, `jobNamespace`).
- Шаблоны отрисованы заменой `helm template`: Go `text/template` с теми же функциями. Каждый документ разобран как YAML.
- Полученный `frood.yaml` для каждого примера проходит `frood plan`.
- В CI добавлена задача `chart` с `helm lint` и `helm template` на примерах.
- Тесты: ядро — 179, runtime-k8s — 15, runtime-docker — 7 (и 1 пропущенный, ему нужен Docker). clippy с `-D warnings` и `fmt --check` чистые. Платных вызовов моделей не было.

### Что не проверено без кластера

- Настоящий RBAC и допуск Pod Security.
- Права на PVC с `fsGroup` у конкретного драйвера хранилища.
- NetworkPolicy к API-серверу: зависит от CNI.
- Ротация логов kubelet на длинном ходе.
- Сборка образов.
- Ограничения на число процессов в поде нет, в отличие от `--pids-limit` в Docker.

## 5. Как сделано / W4: один бот на две установки

### Что делает

Один бот Telegram обслуживает личный Frood и рабочий. Опрашивает бота только личный модуль `telegram`: Telegram отдаёт обновления одному опрашивающему. Рабочий модуль бота не опрашивает. Он получает переданные обновления, обрабатывает их как свои и сам отвечает тем же токеном бота.

Всё новое выключено, пока нет `config.link`. Одна установка со своим ботом работает как раньше: без меток, без пометок на кнопках, без новых запросов.

### Конфиг

Личная установка (VPS):

```yaml
modules:
  telegram:
    image: ghcr.io/froodai/telegram:<version>
    secrets: [TELEGRAM_BOT_TOKEN, TELEGRAM_LINK_TOKEN]
    volumes: [./telegram-data:/data]
    config:
      language: ru
      state_dir: /data              # необязательно: где хранить выученные слова
      link:
        name: Работа                # метка другой установки
        url: https://work.example.com
```

Рабочая установка (Kubernetes, Helm):

```yaml
telegram:
  enabled: true
  linkToken: { existingSecret: frood-telegram-link, key: TELEGRAM_LINK_TOKEN }
  persistence: { enabled: true }   # необязательно: выученные слова переживут перезапуск пода
  config:
    language: ru
    label: Работа                   # необязательно: по умолчанию «Работа» у forwarded
    link:
      mode: forwarded
      name: Личное
      url: https://me.example.com
      words: [PROJ]                 # необязательно: свои рабочие слова сверх данных Frood
```

- `label` — метка этой установки. По умолчанию «Личное» у опрашивающей стороны и «Работа» у `forwarded`, на языке бота. Метки до 40 символов и разные.
- `link.token` — общий токен обеих сторон, не короче 32 символов: `openssl rand -hex 32`. Его можно задать в `link.token` (`${secret:…}`) или переменной `TELEGRAM_LINK_TOKEN`. В Helm конфиг модуля не подставляет секреты, поэтому там только переменная: `telegram.linkToken`.
- `link.url` — адрес Frood другой стороны: `https://…` или `http://` к сервису внутри установки. Это проверяют и `frood plan`, и сам модуль.
- `link.channel` — имя канала у другой стороны, по умолчанию `telegram`.

### Куда идёт сообщение

Личный модуль решает сам, по порядку. Текст в LLM не уходит.

1. **Ответ на сообщение бота.** Установку называет метка в первой строке сообщения или пометка на его кнопках.
2. **Приставка.** «работа:» или «личное:», а также настроенные метки, без учёта регистра. Приставка срезается. Одна приставка без текста переключает разговор: «Следующие сообщения пойдут в «Работа»».
3. **Рабочие слова.** Рабочий Frood отдаёт хеши слов, личный сравнивает с ними слова сообщения. Совпало — сообщение рабочее.
4. **Личные слова.** Слова, которые автор сам назвал личными. Они же убирают совпадения из п. 3.
5. **Продолжение.** В течение 10 минут после сообщения автора — в ту же установку.
6. **Иначе бот спрашивает** «Личное или Работа?» двумя кнопками. Сообщение ждёт ответа только в памяти. Через час без ответа оно удаляется, а вопрос меняется на «Ответа не было час, поэтому сообщение не сохранено. Пришлите его ещё раз.». Ждут не больше 100 сообщений. Сто первое вытесняет самое старое, и его вопрос меняется на «Этот вопрос уже не действует, пришлите сообщение ещё раз.».

На вопрос отвечает только автор сообщения. Чужое нажатие с теми же данными получает «Этот вопрос уже не действует», сообщение ждёт дальше.

Нажатие кнопки идёт туда, чья это кнопка: у рабочих кнопок пометка `~` в начале `callback_data`. Личный модуль такие нажатия не читает, а передаёт. Данные кнопки присылает клиент, поэтому одной пометке личный модуль не верит. Если у сообщения под кнопкой свои, непомеченные кнопки или метка личной установки, нажатие остаётся у личной.

### Команды

- `/start`, `/help` — личная установка.
- `/start l-КОД` — рабочая. Ссылка привязки из рабочей консоли несёт приставку `l-`, рабочий модуль снимает её перед обработкой.
- `/link`, `/unlink` — личная. Рабочая — с приставкой («работа: /link КОД») или с кодом `l-…`.
- `/now`, `/inbox`, `/digest`, `/new` — обе. Каждая отвечает сама, со своей меткой.
- `/ask` и вопросы — по содержимому, как обычный текст.
- Остальные команды — личная.

### Метки

С `link` каждое сообщение бота начинается с метки установки отдельной строкой, жирным в HTML. Метку ставят `sendMessage` и `editMessageText`. Служебные сообщения маршрутизатора (вопрос, «доставлю позже», переключение) идут без метки.

### Передача рабочему Frood

Личный модуль отправляет `POST {link.url}/v1/channels/telegram/link` с `Authorization: Bearer <токен связи>`. Тело — `{op: "update", update, learn}`. Ядро рабочего Frood принимает вызов и передаёт его модулю как вызов возможности `channels.link@1`. Токен связи модуль получает в заголовке `x-frood-link-token` и сам сравнивает за постоянное время. Ответы: 202 принят, 401 неверный токен, 404 связи нет.

**Почему здесь.**
- У модуля нет своего публичного адреса, у ядра есть. Ingress, TLS и путь `/v1` в обход прокси входа уже настроены.
- Вызов ядра к модулю — это уже существующий вызов возможности, с токеном модуля. Нового входа в модуль снаружи нет.
- Ядро токена связи не хранит, тело не читает и не пишет в журнал. Без `channels.link@1` в манифесте модуля ответ 404.

Ещё два вызова того же адреса: `{op: "words"}` отдаёт хеши рабочих слов, `{op: "forget", hashes}` убирает выученные слова.

### Если рабочий Frood недоступен

Обновление ждёт в очереди в памяти, не больше 500 обновлений. Сверх этого новое не сохраняется, и бот один раз пишет: «„Работа“ давно не отвечает, и сообщений в очереди слишком много: это не сохранено. Пришлите его позже.». Повтор через 2 секунды, дальше вдвое дольше, до 2 минут. Автору один раз за перерыв бот пишет: «„Работа“ сейчас не отвечает. Доставлю, когда ответит; если бот перезапустится раньше, сообщение пропадёт». На диск ничего не пишется: **после перезапуска личного модуля недоставленное теряется**. На 400, 401, 403, 404, 413 и 422 повтора нет: бот один раз пишет, что «Работа» не принимает сообщения, и просит проверить токен связи.

### Рабочие слова

Рабочий модуль собирает слова из данных своего Frood: имена и псевдонимы сущностей всех типов, до 200 на тип. Из имени берётся целиком имя до трёх слов, номера вроде `PROJ-123` и ключ `PROJ`. Сюда же — `link.words` и выученные слова. Слово нормализуется: нижний регистр, «ё» как «е», без знаков по краям. Отдаётся только HMAC-SHA256 от слова с токеном связи. Личный модуль берёт список при старте и каждые 10 минут; если не вышло, остаётся прежний. Сравнивает с хешами слов сообщения: отдельные слова, пары и тройки подряд, ключи тикетов. Самих рабочих слов на личном сервере нет. Если ответ пришёл без списка, остаётся прежний.

Хеш не прячет слова от того, у кого есть токен связи: короткие слова и ключи тикетов перебираются быстро. Токен есть у личной стороны. Поэтому хеши защищают от чтения памяти и журналов, а не от самого личного сервера. Так же рабочий модуль может перебрать хеши, которые личный просит забыть.

### Обучение

На вопрос «Личное или Работа?» автор отвечает кнопкой. Из сообщения берутся отличительные слова: номера тикетов, слова с цифрами, слова заглавными, слова с большой буквы не в начале предложения. Не больше пяти, от трёх букв.
- «Работа» — сообщение уходит с `learn: true`, и рабочий модуль запоминает эти слова у себя. Личный модуль убирает их из своих личных, если они там были.
- «Личное» — личный модуль запоминает их открытым текстом у себя и просит рабочий забыть их хеши.

Выученное хранится в `<state_dir>/link-words.json`: у личной стороны — личные слова открытым текстом, у рабочей — рабочие. Файл пишется рядом и переименовывается, поэтому сбой при записи его не портит. Без `state_dir` — только в памяти, до перезапуска. В Helm у модуля `/data` по умолчанию `emptyDir`, и рабочие выученные слова живут до перезапуска пода. С `telegram.persistence.enabled: true` `/data` лежит на томе (PVC), а `state_dir: /data` ставится в конфиг сам.

### Mini App

Кнопка меню одна — личного бота. Рабочий модуль её не ставит. Каждый модуль сообщает своему ядру в `PUT /v1/channels/telegram/about` поле `link`: свою метку, чужую, адрес чужого Mini App (`<link.url>/admin/m/`, только https) и кто первый. Ядро хранит это в `channel_about.link` (миграция 0020) и возвращает при входе в Mini App (`POST /oauth/telegram`).

С `link` на главном экране Mini App переключатель «Личное / Работа». Нажатие открывает Mini App другой установки на месте: `location.assign(<адрес>#tgWebAppData=…&tgWebAppVersion=…&tgWebAppPlatform=…&tgWebAppThemeParams=…)`. Скрипт Telegram на той странице читает данные запуска из hash, как при обычном открытии. Другая установка проверяет подпись Telegram сама: подпись Ed25519 над id бота, а бот один. Её данные через личный сервер не идут. Адрес переключателя берётся только из ответа своего сервера, не из параметров страницы.

Список разрешённых входов рабочей установки (`auth.allow`) действует как раньше: в рабочий Mini App войдёт только привязанный аккаунт из списка.

Данные запуска подписаны для бота, а бот один. Значит, сервер, который их получил, сутки может войти с ними и в Mini App другой установки. Так и с кнопками Mini App в сообщениях рабочей установки. Это цена одного бота: обе установки доверяют друг другу так же, как токену связи.

### Мелкие решения

- Сообщения маршрутизатора без метки: они не от установки.
- Пометка кнопок — один байт `~`. Самые длинные данные кнопок модуля — 47 байт, с пометкой 48, предел Telegram — 64.
- Вопрос «Личное или Работа?» приходит ответом на сообщение автора. Порядок кнопок: опрашивающая сторона первая.
- С токеном связи можно действовать в рабочем Frood от имени автора в Telegram: рабочий модуль принимает переданное обновление как своё. Поэтому токен длинный и случайный и лежит только в секретах.
- Рабочий модуль сообщает ссылку привязки `https://t.me/<бот>?start=l-`. По ней личный модуль узнаёт рабочий `/start`.
- Когда автор отвечает на вопрос, разговор запоминает установку на 10 минут, как после обычного сообщения.

### Проверки

- Модуль `telegram`: 52 теста, среди них сценарии с поддельными Telegram, Frood и рабочей стороной: метки, пометки, токен, недоступность и повтор, рабочие слова, вопрос и удаление через час, обучение.
- Ядро: передача вызова модулю, ответ 401 без токена и 404 без модуля, проверка `link` в about, `link.url` в конфиге. Тест входа в Mini App с `link` требует Postgres и проходит в CI. Локально он пропущен.
- Консоль: тест данных запуска в hash, как их читает скрипт Telegram.

### Что не проверено

- Настоящий бот и две настоящие установки.
- Переключатель в Mini App внутри клиентов Telegram, особенно в Telegram Web: там Mini App — iframe, и переход на другой адрес внутри него не пробовали.
- Нагрузка: обновления передаются по одному.

## 6. Источники рабочего Frood: Glean

### Что читаем

- **Сначала Glean.** Это поиск компании по её Slack, трекерам и документам. У Glean есть свой MCP-сервер, и ночной проход читает его как обычный источник.
- **Slack — через Glean.** Отдельно Slack не подключаем.
- **Прямое приложение Slack — потом и только если Glean что-то упускает.** Такому приложению нужно ревью приложений в компании.

### Как подключить

Источник подключается в консоли: «Источники» → «Подключить источник» → «Glean». Адрес — `https://<instance>-be.glean.com/mcp/default`, где `<instance>` — имя экземпляра компании. Дальше «Войти»: автор входит в Glean своим рабочим аккаунтом, токен копировать не нужно.

Как Frood входит:
- Сервер отвечает 401 и называет свои метаданные в `WWW-Authenticate`. Метаданные лежат по пути ресурса (RFC 9728).
- Сервер входа — путь `/oauth` того же хоста. Его метаданные Frood ищет со вставкой пути: `/.well-known/oauth-authorization-server/oauth` (RFC 8414). Чужой `issuer` Frood не берёт.
- Frood регистрируется сам, как публичный клиент без секрета (RFC 7591, `none`). Вход — PKCE с S256, в запросах есть `resource`.
- Frood просит scope `mcp`: его называет сам сервер. Ещё он просит `offline_access`, если сервер его знает: без него refresh-токена может не быть. Все остальные scope сервера Frood не просит.
- Refresh-токен меняется при каждом обновлении. Frood хранит новый и обновляет по одному: второе обновление тем же токеном сервер посчитал бы повтором.
- Токен входа уходит только на сервер, для которого выдан. Сменить адрес источника можно только новым входом, а проверка с сохранённым токеном идёт только по сохранённому адресу.

Инструменты по умолчанию — `search` и `read_document`. Чат и агенты Glean не выбраны: их ответы — пересказ, а не цитата.

В `frood.yaml` такой источник не записать: вход живёт в консоли. Консоль хранит его так:

```yaml
sources:
  glean:
    uses: mcp
    server: https://<instance>-be.glean.com/mcp/default
    headers: { Authorization: 'Bearer ${oauth:source.glean}' }   # токен входа, его обновляет Frood
    tools: [search, read_document]
    private: true
    scope: "Что изменилось с прошлого прохода и касается меня: …"
```

А в `frood.yaml` — вход одного человека и расписание прохода:

```yaml
auth:
  allow: [me@work.example]          # только автор; allow_domains не задан
jobs:
  daily-sweep:
    on:
      - { schedule: '0 6 * * 1-5', timezone: Europe/Amsterdam, for_each: source }
```

### Проход по поиску

У поиска нет ленты «что нового». Поэтому стандартные инструкции `daily-sweep` для такого источника говорят:
- искать созданное и изменённое со времени прошлого прохода;
- искать про автора: что он написал, где его упомянули или спросили, что по его проектам; проекты брать из Frood;
- важные документы читать целиком, а не по отрывку из поиска;
- к каждой находке — точная цитата и ссылка на документ;
- чат Glean не звать.

Первое сообщение прохода называет человека, чей это источник.

### Вход раз в месяц

Refresh-токен Glean живёт около месяца. Потом обновить вход нельзя, нужно войти снова.
- Frood понимает отказ сервера (`invalid_grant`) и помечает вход как истёкший. Повторять он не пытается.
- В консоли на карточке источника написано «Войти снова». Внутри — пояснение и кнопка «Войти снова». Инструменты и настройки после входа остаются.
- Проход по источнику падает сразу, без повторов, с причиной «source glean: the sign-in ran out (…); sign in again in the console…».
- В сводке упавший запуск назван вместе с источником: «daily-sweep · glean».
- Если три рабочих дня ничего нового, строка «Frood заглох» говорит, что источник glean отказал в доступе.

### Частный источник

Некоторые компании разрешают такой доступ только для личного пользования одного человека: данные нельзя показывать или передавать другим. Glean к тому же отвечает тем, что видно именно этому человеку. Поэтому у источника есть пометка `private: true`, в консоли — переключатель «Только для меня». У Glean он включён сразу.

В Frood все пользователи установки видят всё знание (D9″). Разделять видимость внутри установки Frood не умеет, и делать этого мы не стали. Частный источник работает только в установке одного человека. Frood проверяет это в трёх местах:
- `frood plan`: у частного источника `auth.allow` называет ровно одного человека, `allow_domains` пустой. Домен компании в `allow_domains` не подойдёт. Частные источники из консоли `plan` видит, когда база доступна.
- Перед каждым чтением источника: войти может только этот человек, и ни у кого другого нет живого токена или привязанного чата. Иначе проход падает и называет, кто ещё может читать.
- В консоли: пометить источник частным может только сам этот человек.

Сессия браузера живёт неделю. Если человека убрали из `auth.allow`, его сессия больше не действует: чтобы получить токен, ему нужно войти снова, и вход откажет.

`frood export` с частным источником отказывается и просит `--include-private`: папку экспорта можно кому-то отдать.

Сфер это не касается: сфера в Frood — метка для чтения, а не доступ. Связь с личной установкой (§5) — тот же человек; в неё уходят только хеши рабочих слов.

### Что проверено

- Тест с поддельным сервером в форме настоящих метаданных Glean: путь ресурса, `scope` в вызове, сервер входа по пути, регистрация, PKCE, `resource`, смена refresh-токена, отказ старого токена.
- Тест с базой: истёкший вход виден в консоли, проход получает «sign in again», частный источник без одного человека не подключается. Он требует Postgres и идёт в CI.
- Настоящий вход в Glean не пробовали. Не проверено, что Glean выдаёт refresh-токен на `mcp offline_access` и что ссылка на документацию Glean в консоли живая.
