# M12. Рабочий Frood — предложение

> Статус: принято частично (раунд 29, 23.11): QW2, QW3, W1; QW1 открыт.
> Основание: автор в Cockpit 23.11 — у него два пространства, личное и рабочее; корпоративные данные не должны лежать на личном VPS; рабочий Frood он хочет во внутренней Kubernetes-платформе компании со своим рабочим аккаунтом Google, а личный VPS оставить для личного. В замысле личная и рабочая установки уже раздельны: решение D9″ в [журнале решений](README.md#журнал-решений) — «пользователи без пространств и ролей, разделение инсталляциями».

## 0. Что вижу

**Внутренняя платформа компании.**
- Веб-консоль поверх Kubernetes, свой namespace (место в кластере) создаётся самим автором.
- Деплой — образ из реестра контейнеров и Helm-чарт через CI. Можно и `kubectl` со своей машины.

**Что подходит сразу.**
- Postgres: управляемая база, адрес и пароль приходят Secret'ом, бэкапы настраиваются на стороне платформы. Frood нужны расширения `vector`, `pg_trgm`, `btree_gist`; доступность каждого надо уточнить у администраторов платформы.
- Бакет с S3-совместимым доступом — для файлов и бэкапов.
- Ingress с TLS: внутренний адрес, доступный только из корпоративной сети и VPN, или публичный.
- Вход через рабочий аккаунт Google (OIDC) — Frood уже умеет.

**Что мешает.**
- **ИИ.** Политика ИИ компании запрещает личные подписки на рабочих данных. Нужен корпоративный путь к модели: ключ API с оплатой компании или внутренний шлюз.
- **Агенты.** Сейчас Frood запускает агента в Docker-контейнере на своей машине, а в кластере Docker нет. Нужен рантайм для Kubernetes: каждый ход агента — отдельная задача (Job) в namespace автора.
- **Развёртывания в Kubernetes у Frood нет.** Нужны Helm-чарт и образы без root.
- **Чат.** Компания предпочитает свой корпоративный чат, а не Telegram.
- Новый внутренний сервис, который читает рабочие системы, скорее всего проходит ревью безопасности.

**Заодно про личный VPS.** По той же политике проход по рабочему трекеру на VPS через подписку автора тоже не разрешён. Выключим, как скажет автор.

## 1. Предлагаю: этап M12 «Рабочий Frood»

- **W1 — код:** поддержка ключа API для агентов, рантайм агентов для Kubernetes, Helm-чарт. Это можно делать сразу.
- **W2 — установка:** namespace, Postgres, вход, первый проход по рабочему трекеру. Рабочее с VPS переносим и удаляем, включая бэкапы.
- **W3 — корпоративный чат:** модуль чата вместо Telegram, если понадобится.
- **Параллельно:** вопросы администраторам платформы (расширения Postgres, выход в интернет), по ключу API и по ревью безопасности. Если автор скажет — подготовлю тексты.

## 2. Вопросы

**QW1. Откуда открывать рабочий Frood:**
- (а) только из корпоративной сети и VPN: консоль, Claude Code, Air; наружу ничего не торчит;
- (б) и снаружи: Claude на телефоне, коннектор claude.ai. Нужен публичный адрес, ревью строже.

Я предлагаю (а): проще и безопаснее. Снаружи добавим, если понадобится.

**QW2. Через что рабочий Frood зовёт Claude:**
- (а) ключ API с оплатой компании;
- (б) внутренний шлюз компании;
- (в) подписка автора — политика запрещает.

Я предлагаю (а), а если ключей для сервисов не дают — (б). В Frood это одна доработка: адрес шлюза и токен.

**QW3. Куда рабочий Frood присылает сводку:**
- (а) корпоративный чат: новый модуль и ревью безопасности нового приложения;
- (б) Telegram, как личный, — компания предпочитает свой чат;
- (в) пока только консоль, без уведомлений.

Я предлагаю (а), а пока делается — (в).

## 3. Решения (раунд 29, 23.11)

- **QW2:** у автора есть оплата компании за API для рабочих данных, поэтому рабочая установка ходит к Claude по ключу API с оплатой компании, а не по подписке.
- **QW3:** Telegram, а не корпоративный чат. Рабочей установке нужен свой бот: один бот опрашивается только одной установкой.
- **W1 принято:** «делай доработки». Это рантайм агентов для Kubernetes, Helm-чарт и аккаунты с ключом API для задач агентов.
- **QW1:** ответа пока нет; чарт поддерживает оба варианта — внутренний и публичный ingress.
