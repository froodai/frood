# M12. Рабочий Frood — предложение

> Статус: принято (раунд 29, 23.11): QW1, QW2, QW3, W1. W1 сделан, см. §4.
> Основание: автор в Cockpit 23.11 — у него два пространства, личное и рабочее; корпоративные данные не должны лежать на личном VPS; рабочий Frood он хочет во внутренней Kubernetes-платформе компании со своим рабочим аккаунтом Google, а личный VPS оставить для личного. В замысле личная и рабочая установки уже раздельны: решение D9″ в [журнале решений](README.md#журнал-решений) — «пользователи без пространств и ролей, разделение инсталляциями».

## 0. Что вижу

**Внутренняя платформа компании.**
- Веб-консоль поверх Kubernetes, свой namespace (место в кластере) создаётся самим автором.
- Деплой — образ из реестра контейнеров и Helm-чарт через CI. Можно и `kubectl` со своей машины.

**Что подходит сразу.**
- Postgres: управляемая база, адрес и пароль приходят Secret'ом, бэкапы настраиваются на стороне платформы. Frood нужны расширения `vector`, `pg_trgm`, `btree_gist`; доступность каждого надо уточнить у администраторов платформы.
- Бакет с S3-совместимым доступом — для файлов и бэкапов.
- Ingress с TLS: внутренний адрес, доступный только из корпоративной сети и VPN, или публичный.
- Вход через рабочий аккаунт Google (OIDC) — Frood уже умеет.

**Что мешает.**
- **ИИ.** Политика ИИ компании запрещает личные подписки на рабочих данных. Нужен корпоративный путь к модели: ключ API с оплатой компании или внутренний шлюз.
- **Агенты.** Сейчас Frood запускает агента в Docker-контейнере на своей машине, а в кластере Docker нет. Нужен рантайм для Kubernetes: каждый ход агента — отдельная задача (Job) в namespace автора.
- **Развёртывания в Kubernetes у Frood нет.** Нужны Helm-чарт и образы без root.
- **Чат.** Компания предпочитает свой корпоративный чат, а не Telegram.
- Новый внутренний сервис, который читает рабочие системы, скорее всего проходит ревью безопасности.

**Заодно про личный VPS.** По той же политике проход по рабочему трекеру на VPS через подписку автора тоже не разрешён. Выключим, как скажет автор.

## 1. Предлагаю: этап M12 «Рабочий Frood»

- **W1 — код:** поддержка ключа API для агентов, рантайм агентов для Kubernetes, Helm-чарт. Это можно делать сразу.
- **W2 — установка:** namespace, Postgres, вход, первый проход по рабочему трекеру. Рабочее с VPS переносим и удаляем, включая бэкапы.
- **W3 — корпоративный чат:** модуль чата вместо Telegram, если понадобится.
- **Параллельно:** вопросы администраторам платформы (расширения Postgres, выход в интернет), по ключу API и по ревью безопасности. Если автор скажет — подготовлю тексты.

## 3. Решения (раунд 29, 23.11)

- **QW1:** без VPN: публичный адрес, вход через Google, только рабочие аккаунты; Frood проверяет вход сам, прокси перед ним необязателен.
- **QW2:** корпоративный шлюз, совместимый с Anthropic API: адрес шлюза и ключ от команды-помощника; личная подписка не используется.
- **QW3:** Telegram, а не корпоративный чат. Рабочей установке нужен свой бот: один бот опрашивается только одной установкой.
- **W1 принято:** «делай доработки». Это рантайм агентов для Kubernetes, Helm-чарт и аккаунты с ключом API для задач агентов.

## 4. Как сделано / W1

### Модели через шлюз

**Аккаунт.** У аккаунта `kind: api_key` ключ задаётся одним из двух способов:
- `secret` — сам ключ;
- `api_key_helper` — команда, которая печатает ключ. Это для шлюзов, которые выдают короткоживущие ключи.

Задать оба способа или ни одного — ошибка конфига. Необязательный `base_url` — корень API шлюза без `/v1`. Это `https://…` или `http://` к адресу внутри установки: loopback, имя сервиса Compose без точек, имя Service в Kubernetes (`*.svc`, `*.svc.cluster.local`). Код — `frood-config`.

**Прямые вызовы ядра.** Сервер шлёт запросы на `base_url`. Команду `api_key_helper` он запускает через `sh -c`, ключ из её вывода держит пять минут, а после ответа 401 запускает команду ещё раз и повторяет запрос. Если команда упала, в ошибку попадает её stderr, а stdout — нет: там может быть ключ. Код — `frood-llm`.

**Агенты.** Рантайм получает в `credentials` поле `base_url`, а также `api_key` или `api_key_helper`.
- Claude Code получает `ANTHROPIC_BASE_URL`. Ключ приходит в `ANTHROPIC_API_KEY` либо в настройку `apiKeyHelper` (`--settings`). Во втором случае Claude Code сам запускает команду внутри контейнера агента, поэтому команда должна быть и в образе сервера, и в образе агента.
- Codex получает `OPENAI_BASE_URL` с `/v1`. Аналога `apiKeyHelper` у Codex нет, поэтому `api_key_helper` для него отклоняют и валидация конфига, и рантайм.
- Подписке `base_url` не положен.

Код — общий `agents.rs` у runtime-docker и runtime-k8s. Контракт описан в `contracts/agents.execute/1`.

### runtime-k8s: агенты как задачи Kubernetes

**Ход агента.** Каждый ход — Job из одного пода, в namespace модуля или в `namespace`. Порядок шагов:
1. Job создаётся приостановленным (`suspend: true`).
2. Рядом создаётся Secret с env и аргументами хода. Его владелец — этот Job.
3. Job отпускают патчем `suspend: false`.

Ключ, промпт и токен запуска лежат только в Secret. В спецификации Job — ссылки `secretKeyRef` и аргументы вида `$(FROOD_ARG_n)`.

**Сессии.** Сессии запуска живут на отдельном PVC `frood-run-<run_id>`: это домашний каталог агента. Init-контейнер создаёт на нём рабочую папку. `stop` удаляет Job и PVC, Secret уходит вместе с Job.

**Под.**
- Пользователь 10001, `runAsNonRoot`, без повышения привилегий, все capabilities сброшены.
- Корневая файловая система только для чтения, `/tmp` — `emptyDir`.
- Seccomp `RuntimeDefault`, без токена API.
- `requests` равны лимитам.

Под проходит стандарт `restricted`.

**Время и отмена.**
- `activeDeadlineSeconds` равен `max_minutes` плюс минута: ход кончается, даже если `stop` не пришёл.
- Ядро, как и раньше, само шлёт `stop` по бюджету минут и при отмене.
- Job, который модуль не успел убрать (например, лежал), удалит TTL (`keep_finished_minutes`).
- Ход падает с понятной причиной, если: образ не скачивается, упал init-контейнер, под вытеснили, истёк срок, Job исчез.

**Права.** Только Role в своём namespace:

| Ресурс | Права |
|---|---|
| Jobs | create, get, patch, delete |
| Pods | list |
| pods/log | get |
| PVC | create, delete |
| Secrets | create |

Читать Secrets модуль не может.

**API.** Модуль ходит в API кластера по HTTPS с токеном своего ServiceAccount и перечитывает токен на каждый запрос. Watch нет: ядро опрашивает `status`.

**Где агент находит Frood.** Под агента находит Frood по `frood_url` — полному имени Service, например `http://frood.<namespace>.svc:8080`. Чарт задаёт его сам.

**Проверка.** Юнит-тесты гоняют модуль против API-сервера в памяти (`src/mock.rs`). Этот мок исполняет поддельного агента, проверяет правила `restricted` и умеет просроченный срок и отказ RBAC. Тесты проходят:
- вопрос и возобновление в той же сессии;
- `stop`;
- падение и образ, который не скачивается;
- срок и отказ RBAC: 503 с повтором, том убран;
- ключ от команды-помощника: его нет ни в Job, ни в Secret.

### Helm-чарт `deploy/helm/frood`

**Сервер.**
- `frood.yaml` лежит в ConfigMap. Чарт сам дописывает `listen`, `public_url` (из ingress), `storage`, `deploy` и адреса модулей.
- Адрес базы берётся из готового Secret, остальные `${secret:…}` — из Secret через env.
- Токены модулей создаются один раз и сохраняются при обновлениях.
- Пробы: `/healthz` (startup и liveness) и `/readyz`.

**Файлы.** Три варианта:
- PVC — тогда одна реплика и `Recreate`;
- бакет S3;
- база.

**Вход.** По умолчанию публичный ingress, вход проверяет сам Frood (Google, `allow_domains`). Класс ingress, хост и issuer cert-manager задаются в values, поэтому так же ставится и только внутренний адрес.

Прокси входа перед консолью (external auth у ingress-nginx) включается отдельно. Пути `/mcp`, `/oauth`, `/.well-known` и `/v1` идут через второй Ingress без прокси: их клиенты носят токены Frood, а не браузерную сессию.

**Агенты.** runtime-k8s ставится со своими ServiceAccount, Role и RoleBinding. Агенты могут работать в другом namespace (`agents.jobNamespace`).

**Модули по желанию.**
- Telegram: одна реплика, `Recreate` — двое опрашивающих одного бота мешают друг другу.
- backup-restic: с PVC файлов он работает на узле сервера и читает файлы только для чтения.

**Сеть.** NetworkPolicy включается отдельно. Она открывает выход:
- в DNS;
- в интернет без частных диапазонов;
- к частным адресам из values (Postgres, шлюз);
- к подам релиза;
- модулю агентов — к API-серверу.

Входящие к модулям пускаются только от сервера, к подам агентов — ни от кого.

**Шлюз рядом.** Через `extraObjects` рядом можно поставить прокси шлюза: Deployment и Service. `base_url` указывает на имя этого Service. Пример `examples/llm-gateway.yaml` условный, без настоящего продукта.

**Образы.** Все образы теперь объявляют числового пользователя (`USER 10001`): иначе Kubernetes не может проверить `runAsNonRoot`. runtime-docker по-прежнему работает от root: ему нужен Docker хоста.

**Проверка.**
- `helm` на машине не установлен, поэтому `helm lint` и `helm template` локально не запускались.
- Шаблоны отрисованы заменой `helm template`: Go `text/template` с теми же функциями. Каждый документ разобран как YAML.
- Полученный `frood.yaml` для каждого примера проходит `frood plan`.
- В CI добавлена задача `chart` с `helm lint` и `helm template` на примерах.
- Тесты: ядро — 179, runtime-k8s — 15, runtime-docker — 7 (и 1 пропущенный, ему нужен Docker). clippy с `-D warnings` и `fmt --check` чистые. Платных вызовов моделей не было.

### Что не проверено без кластера

- Настоящий RBAC и допуск Pod Security.
- Права на PVC с `fsGroup` у конкретного драйвера хранилища.
- NetworkPolicy к API-серверу: зависит от CNI.
- Ротация логов kubelet на длинном ходе.
- Сборка образов.
- Ограничения на число процессов в поде нет, в отличие от `--pids-limit` в Docker.
