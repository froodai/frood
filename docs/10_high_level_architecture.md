## 1. Суть в одном абзаце

В центре стоит своё небольшое **ядро знаний (Knowledge Ledger)**, единственный источник истины. Это двухвременной (bitemporal) журнал утверждений, их источников, предложений об изменении и решений человека. Всё остальное — заменяемые модули вокруг ядра: ввод (capture, sources), агенты (определения отдельно, рантаймы отдельно), событийный движок, перестраиваемые проекции для поиска и графа, поверхности доступа (MCP, HTTP, мессенджеры, веб). **Агенты никогда не пишут в знания напрямую.** Они создают предложения (аналог PR), которые принимает человек или явная политика.

## 2. Схема слоёв

```
 SURFACES   Claude · ChatGPT · Codex/Claude Code · OpenClaw/Hermes   Web Inbox   Telegram/Slack bot   ntfy   CLI
                  └───────────── MCP (+ MCP Apps) ─────────────┘     └──────────── HTTP API ────────────┘
                                          │                                   │
 ACCESS     ─────────── AuthN/Z: OAuth 2.1 (CIMD/DCR), scopes read / propose / decide / admin ───────────
                                          │
 CORE       ┌──────────────── Knowledge Ledger (любое хранилище по контракту) ───────────────────┐
            │  Sources/Evidence ─▶ Observations ─▶ Proposals ──decide──▶ Assertions (bitemporal) │
            │  provenance · epistemic status · supersede/retire · Decisions · Audit · Outbox     │
            └───────────────┬──────────────────────────────────────────────────▲────────────────┘
                            │ events (CloudEvents)                              │ только proposals
 WORK       Triggers (правила по событиям, cron + checkpoints) ─▶ Durable work items ─▶ Runner adapters
                            │                                                   │
 AGENTS     Agent Definitions (Agent Skills + policy + output contract)  ×  Agent Runtimes (SDK / ACP / cloud)
                            │  инструменты агента: Memory MCP (scoped token) + MCP-серверы источников
 INPUT      Capture (текст / голос / файлы / встречи) · Source connectors (Slack, Docs, YouTrack…) · STT / parsing
 READ       Projections: current view · hybrid search · entity graph · context packs · Markdown/JSONL export
 PLATFORM   module manifests & capabilities · frood.yaml → Compose · secrets · LLM gateway · backups · attention
```

## 4. Ключевые сквозные потоки

**A. Быстрый сброс (голос).** Голосовуха в Telegram → object store → STT → Observation → извлечение (LLM) → Proposal(s) → политика «мои собственные утверждения принимаются автоматически, если нет конфликта» → Assertion → событие → обновление проекций. Если найден конфликт, вместо авто-принятия создаётся Decision.

**B. Ночной проход.** Cron → по каждому источнику берётся checkpoint → дельта с последнего успешного прохода → агент `daily-sweep` (любой рантайм) читает дельту и контекст через Memory MCP → создаёт Proposals (новое / конфликт / замена / устаревание) → Attention решает: утренний дайджест или немедленный push → человек решает в Inbox, Telegram или чате → Ledger.

**C. Доступ из чата.** Claude (web/desktop/mobile), ChatGPT (web), Codex, Claude Code → Memory MCP (OAuth, scope `read+propose`) → `search` / `get_context`; новые факты уходят как `propose`, не `approve`.

**D. Жизненный цикл проекта.** Событие «PR смержен / эпик закрыт» (вебхук или обнаружено в sweep) → агент `lifecycle-review` → пачка Proposals (`historical` / оставить актуальным) → Inbox.

**E. Перепроверка.** У утверждения есть `review_after` → work item → агент проверяет источники → предлагает оставить или признать неактуальным.

## 5. Инварианты

1. Ledger — единственная истина. Проекции, графы и индексы перестраиваются из него. Core стартует **без LLM, графа и чата**.
2. Агенты получают только `read + propose`. `decide` есть только у человека или у явной политики, и каждое такое решение пишется в аудит.
3. Любое изменение знаний идёт по цепочке Proposal → Decision → Assertion, включая авто-принятие.
4. Ничего не удаляется: только `supersede` / `retire` с временем и причиной (bitemporal: valid time + recorded time).
5. **Модульный монолит.** Модуль = контракт (`capability@version`) + манифест + реализация. Отдельный процесс нужен только там, где нужен другой рантайм (STT, граф, бот).
6. Личная и корпоративная инсталляции — разные deployments одного кода, данные между ними не ходят.
7. Открытые форматы: CloudEvents для событий, OpenAPI + MCP для API, Agent Skills для инструкций, JSONL/Markdown для экспорта.

## 6. Решения

| ID | Решение | Статус |
|---|---|---|
| D1′ | Канон — собственный модуль Ledger со своей моделью данных. Хранилище под ним — любое, удовлетворяющее контракту (транзакции, журнал, см. 11 §12). Memory-движки и графы — только проекции | принято |
| D2 | Все записи агентов — Proposals; решают человек или политика. Уточнение: «кто решил в реальности» (authority) отделён от «кто принял в память» (verdict); политики могут доверять авторитетным источникам | принято |
| D3 | HTTP API — основной контракт; MCP — тонкий адаптер для агентов | принято |
| D4 | Источники: готовые MCP-серверы + свои pull-коннекторы с курсором | принято |
| D5 | Определение агента отдельно от рантайма | принято |
| D6′ | Фоновые задачи = очередь с повторами + расписание с догоном + триггеры по событиям + история запусков. Ожидание вердикта не держит процесс: вердикт — запись в Ledger, продолжение запускается событием. Тяжёлый durable workflow engine и брокер сообщений не нужны; движок — деталь реализации | принято |
| D7′ | Модули — пакеты / образы с манифестом. «Маркетплейс» v1 = git-реестр: репозиторий с индексом модулей и бандлов (манифест, версия, ссылка на образ с зафиксированным хэшем). Установка = строка в `frood.yaml` + `frood apply`. Не делаем загрузку кода в работающий процесс | принято |
| D8 | `frood.yaml` → генерация Compose; личная и корпоративная версии — отдельные deployments | принято |
| D9″ | Многопользовательская с v1, но без пространств и ролей: все пользователи инсталляции видят всё и могут ставить вердикты; у каждого своё авторство, Inbox и профиль внимания. Разделение видимости — только отдельными инсталляциями. Следствие: личные источники коллег в общую инсталляцию не подключаются. (D9′ с пространствами подтверждено, но в модели знаний пространства и роли отклонены — M1, M9.) | принято (раунд 3) |
| D10 | Ядро на Rust (единый бинарник, rmcp 3.x поддерживает спеку 2026-07-28 и OAuth). Модули на любом языке через HTTP/MCP-контракты; ML-модули (STT, извлечение) — отдельные процессы, обычно Python | принято |

## 7. Сознательно НЕ делаем в v1

- Multi-user / multi-tenant, marketplace модулей, горячая загрузка стороннего кода.
- Kafka, Kubernetes, отдельный message broker.
- Собственный чат (чатов хватает в существующих агентах).
- Внешние действия ассистента (писать коллегам, менять задачи). В v1 он только ищет, предлагает и спрашивает; контракт `actions.*` оставляем под расширение.

## 8. Порядок детализации после апрува

1. Модель данных Ledger (assertion, proposal, decision, provenance, bitemporal, жизненный цикл).
2. Memory API + MCP + auth (операции, scopes, OAuth, MCP Apps).
3. Work engine + контракт агентного рантайма + формат Agent Definition.
4. Ingestion: capture, STT, источники, checkpoints.
5. Inbox, уведомления, attention-модель.
6. Kernel / манифесты / deploy / backup / версии.
