# Фаза 1. Модель знаний (Ledger), v0.2

> Статус: **v0.1 одобрена с правками 2026-10-17** (ответы в §16). v0.2 убирает пространства и роли; разделение видимости делается инсталляциями. Логическая модель, без привязки к СУБД.
> Референсы: модель утверждений Wikidata (statement + qualifiers + references + rank), W3C PROV (происхождение), SQL:2011 bitemporal (две оси времени), pull request (changeset + base + review), crypto-shredding (удаление в append-only системах).

## 1. Словарь

| Понятие | Что это | Пример |
|---|---|---|
| **Installation** | Одна развёрнутая система. Инсталляции полностью независимы и никак не связаны. Видимость делится только ими | «личная», «рабочая» |
| **User** | Человек с учётной записью в инсталляции. Все пользователи инсталляции видят всё её знание | Алиса, Боб |
| **Principal** | Тот, кто действует: пользователь, агент от имени пользователя, интеграция, политика | `agent:daily-sweep` от имени Алисы |
| **Source** | Внешний артефакт, откуда пришла информация: стабильная ссылка, хэш, время | сообщение в Slack, голосовая заметка |
| **Evidence** | Конкретное место внутри источника | аудио 12:40–13:05, абзац 3 |
| **Observation** | Извлечённое свидетельство, ещё не знание | «Оля пишет, что релиз сдвигается» |
| **Entity** | О чём знание: человек, проект, команда, компонент, встреча, тема | `Project: Orion` |
| **Assertion** | Единица знания: утверждение с видом, сущностями, временем, статусом и доказательствами | «Релиз Orion 2.4 — 28 ноября» |
| **Proposal** | Предложенное изменение знаний, аналог pull request | «Заменить срок 14.11 на 28.11» |
| **Verdict** | Решение по предложению: принять (вариант), с правкой, отклонить, отложить, исследовать | «принят вариант A, Алиса, 11.10» |
| **Event** | Неизменяемая запись журнала о любом изменении | `assertion.superseded` |

Одобрение называется **Verdict**; `decision` — вид утверждения («команда решила X»).

## 2. Связи

```
Source 1──N Evidence N──1 Observation N──N Proposal 1──N Verdict
                                              │ operations
                                              ▼
Entity N──N Assertion (цепочка версий v1 ─superseded_by→ v2 …) ──N Evidence
Assertion ──link──> Assertion   (contradicts / depends_on / part_of / derived_from / relates_to)
Principal ──acts──> Source / Proposal / Verdict / Event
```

## 3. Assertion

Гибрид: **текст + вид + структурированные поля по виду**. Структурированные поля нужны, чтобы работали вопросы вида «какие сроки на этой неделе», «за что отвечает Оля», «какие решения по Orion приняты в октябре»: это запросы с фильтрами по виду, полям и времени. Текст нужен для чтения человеком и LLM. Строгие тройки «субъект-предикат-объект» не берём: хрупко и плохо читается.

| Поле | Смысл |
|---|---|
| `id`, `version` | Стабильный id утверждения и номер неизменяемой версии |
| `kind` | Вид: задаёт схему полей и жизненный цикл |
| `title` | Короткий заголовок, который читают первым (до 120 знаков; с 0.1.5, у старых версий нет) |
| `sphere` | Сфера жизни: `tech`, `business`, `personal` или своя из `frood.yaml` ([26 §3](26_attachments_spheres_connect.md)). Пометка для чтения и фильтров, не граница видимости. Без неё `create` берёт обычную сферу своих сущностей, `supersede` оставляет текущую |
| `text` | Каноническая формулировка — описание под заголовком |
| `subjects` | Сущности, о которых утверждение |
| `slots` | Поля по виду: срок, ответственный, условие, область (JSON Schema вида) |
| `modality` | `mentioned` / `proposed` / `agreed` / `decided` / `reported` / `observed` / `inferred` |
| `authority` | Кто решил или утверждал в реальности и где это зафиксировано |
| `said_at` | Когда сказано в источнике |
| `valid` | `[from, to)` когда действует в реальности |
| `recorded` | `[from, to)` когда эта версия была текущей в памяти |
| `status` | Жизненный цикл (§5) |
| `review_after` | Когда перепроверить |
| `evidence` | Доказательства; для фактов, сообщённых пользователем, — его заметка как источник |
| `links` | Связи с другими утверждениями |
| `origin` | Proposal и Verdict, создавшие эту версию |

### Виды v1 (модули могут добавлять свои)

| `kind` | Что | Поля | Жизненный цикл |
|---|---|---|---|
| `decision` | Договорённость, принятое решение | `decided_by`, `rationale`, `alternatives`, `scope` | Живёт долго; закрывается новым решением |
| `commitment` | Обязательство, срок, план | `owner`, `due`, `deliverable` | `completed` при выполнении; напоминания по `due` |
| `rule` | Правило, инструкция, политика | `scope`, `applies_when` | Перепроверка по `review_after` |
| `responsibility` | Кто за что отвечает | `person`, `area`, `role` | История «кто отвечал на дату» |
| `fact` | Факт о проекте, системе, людях | — | Общий случай |
| `status` | Текущее состояние | `state` | Быстро устаревает |
| `event` | Произошедшее событие | `occurred_at` | Не устаревает, запускает переоценку связанного |
| `open_question` | Нерешённый вопрос | `waiting_on`, `asked_at` | Основа для напоминаний «зависло» |

## 4. Время

`said_at` (когда сказано), `valid [from, to)` (когда действует), `recorded [from, to)` (когда было текущим в памяти).

| Вопрос | Как отвечаем |
|---|---|
| Что верно сейчас? | `valid` содержит now, `recorded.to` открыт |
| Кто отвечал за компонент 1 марта? | `valid` содержит 1 марта, по текущему знанию |
| Что мы знали на 1 марта? | `recorded` содержит 1 марта |

## 5. Жизненный цикл

`active` → `superseded` / `completed` / `historical` / `retired`; флаги поверх `active`: `contested`, `needs_verification`. Переходы — только через принятый Proposal. Закрытие проекта ничего не закрывает автоматически.

## 6. Proposal и Verdict

| Поле Proposal | Смысл |
|---|---|
| `operations[]` | `create`, `supersede`, `close`, `link`, `unlink`, `merge_entities`, `split_entity`, `reclassify`, `reverify`, `set_sphere` |
| `base` | Версии, против которых составлено предложение |
| `alternatives[]` | Варианты для конфликта |
| `rationale`, `evidence` | Почему и на основании чего |
| `author` | Пользователь, агент от имени пользователя, интеграция |
| `risk` | `new` / `change` / `conflict` / `stale_knowledge` / `entity_merge` |
| `confidence` | Оценка уверенности автора-агента (индикатор для политик, не гарантия) |
| `state` | `open` → `accepted` / `rejected` / `deferred` / `stale` |

Вердикты: `accept(alternative?)`, `accept_with_edits(patch)`, `reject(reason)`, `defer(until)`, `investigate(instructions)`. Автор вердикта — пользователь или правило политики. Применение атомарно. Устаревшая база → `stale`, нужна пересборка.

## 7. Authority и verdict

- **authority** — кто принял решение в реальности, плюс где это зафиксировано.
- **verdict** — кто согласился, что это верно попало в память.
- Авторитетные источники (ADR, утверждённые протоколы): решения из них может принимать политика, это видно в аудите.

## 8. Политики авто-вердикта

Правило = условие (вид, источник и его авторитетность, автор, конфликт, риск, уверенность) → действие (`auto_accept`, `require_review`, `notify_only`).

| Случай | По умолчанию |
|---|---|
| Пользователь сам сообщил факт, конфликта нет | авто-принятие (в любой инсталляции, в т.ч. общей рабочей) |
| То же, но есть конфликт | ревью |
| Предложение от агента | ревью |
| Авторитетный источник, `decision` / `rule`, без конфликта | авто-принятие (настраивается) |
| Слияние дублей сущностей, уверенность ≥ порога | авто-принятие; слияние обратимо через `split_entity` |
| Слияние дублей, уверенность ниже порога | ревью |
| Пометка `needs_verification` | без ревью, это флаг |
| Человек переносит знание в другую сферу (`set_sphere`) | авто-принятие (`own-sphere`): меняется пометка, не знание |

## 9. Пользователи (без пространств и ролей)

- **Разделение видимости = инсталляции.** Личная и рабочая — разные инсталляции, никак не связанные.
- **Внутри инсталляции все пользователи видят всё** и могут ставить вердикты. Ролей нет.
- **Пользователь всё равно нужен как сущность:** авторство и аудит («кто предложил, кто принял»), свой Inbox и профиль внимания (кого о чём беспокоить), агенты действуют от имени конкретного пользователя и с его доступами к источникам.
- **Права токенов ≠ роли.** У токена, выданного AI-клиенту или агенту, есть scopes (чтение / предложение / вердикт / ввод); пользователь сам решает, что разрешить клиенту. Это фаза 2.
- **Следствие для общих инсталляций:** всё, что попало в инсталляцию, видно всем её пользователям. Поэтому личные источники коллеги (его личные сообщения) в общую рабочую инсталляцию не подключаются; коннекторы источников настраиваются на уровне инсталляции.
- **Задел на будущее:** пространства можно добавить позже миграцией (всем записям проставляется одно пространство по умолчанию), модель этому не мешает.

## 10. Журнал событий

Любое изменение → неизменяемое событие с монотонной позицией (`source.captured`, `observation.extracted`, `proposal.opened`, `proposal.verdict`, `assertion.created`, `assertion.superseded`, `assertion.closed`, `entity.merged`, `entity.split`, `review.due`, `content.redacted`). Конверт CloudEvents + `actor`, `position`. Состояние и событие пишутся атомарно. Проекции и триггеры читают журнал с checkpoint и могут перестроиться с нуля.

Хранение — неизменяемые версии + журнал, а не чистый event sourcing.

## 11. Удаление

Redaction: содержимое стирается, остаются скелет, связи и факт удаления; проекции вычищают копии. Опция сильнее — crypto-shredding. Корпоративных требований к удалению у автора нет (P3), поэтому в v1 достаточно базового redaction без шифрования по ключам.

## 12. Контракт хранилища

1. Атомарная запись нескольких записей.
2. Согласованное чтение снимка.
3. Упорядоченный журнал с монотонной позицией; состояние и событие атомарно.
4. Ограничения уникальности (одна текущая версия утверждения).
5. Запросы по диапазонам времени и вторичным индексам.

Подходят SQL-СУБД с транзакциями, документные с многодокументными транзакциями, версионируемые. Не подходят как канон: KV без транзакций, векторные БД, графовые движки со своей LLM-экстракцией.

## 13. Операции `knowledge.ledger@v1`

| Команды | Запросы |
|---|---|
| `capture_source` | `get_assertion(id, as_of?, valid_at?)` |
| `add_observation` | `list_assertions(filter по виду, полям, сущностям, статусу, времени; as_of?, valid_at?)` |
| `open_proposal` / `amend_proposal` / `rebase_proposal` | `get_entity(id)` + текущие утверждения |
| `submit_verdict` | `history(assertion \| entity)` |
| `redact(record, reason)` | `list_proposals(filter)` / `inbox(user)` |
| `upsert_user` | `journal(from_position)` |

`search`, `get_context` и ответы на вопросы на естественном языке — модули поверх журнала, не Ledger.

## 14. Сквозной пример

Без изменений относительно v0.1: перенос срока релиза 14.11 → 28.11 через конфликтный Proposal, вердикт Алисы, атомарная замена `A-17 v1` на `A-17 v2`, события в журнале.
