## 1. Ядро: что внутри, что снаружи

Ядро маленькое. Один бинарник на Rust (`frood`) = сервер + CLI.

| Внутри ядра | Почему |
|---|---|
| HTTP API, MCP-адаптер, вход (OAuth-сервер, федерация с внешними провайдерами) | Граница системы и безопасность |
| Ledger (модель знаний, Proposals, Verdicts, журнал) поверх хранилища по контракту | Канон (D1′); само хранилище — модуль |
| Dispatcher, scheduler, очередь запусков | Связывает всё со всем (фаза 3) |
| Хост модулей: клиент реестра, разрешение возможностей, вызов модулей | Модульность |
| Загрузка и проверка конфига, секреты, ревизии | Декларативность |
| Миграции, здоровье, наблюдаемость (сбор) | Обновления и диагностика |

Всё остальное — модули: хранилище, поиск и граф, LLM gateway, рантаймы агентов, распознавание и разбор, источники, каналы, маршрутизатор внимания, админ-панель, бэкапы, цель деплоя. Ядро стартует без LLM, графа и чата (инвариант).

## 2. Модуль

### Манифест `frood-module.yaml`

```yaml
name: google-drive
version: 0.4.2
description: Pull-коннектор Google Drive
license: Apache-2.0
provides:
  - sources.pull@1
requires:
  - storage.objects@1            # если нужно где-то хранить
config:                          # JSON Schema настроек
  type: object
  properties:
    folder: { type: string }
  required: [folder]
permissions:
  egress: [www.googleapis.com, oauth2.googleapis.com]
  secrets: [google_oauth]        # только объявленные секреты
  frood_api: [knowledge:capture] # scopes сервисного токена
events:
  produces: [source.captured]
runtime:
  form: container                # builtin | container | bundle
  image: ghcr.io/frood/google-drive@sha256:…
  health: /healthz
migrations: none                 # или каталог миграций, если модуль хранит данные
```

### Три формы

| Форма | Что | Примеры |
|---|---|---|
| **builtin** | Скомпилирован в бинарник ядра (Rust) | Ledger, вход, dispatcher, встроенный MCP-адаптер источников, базовый LLM gateway |
| **container** | Отдельный процесс на любом языке, говорит по HTTP-протоколу модулей | Распознавание речи, разбор документов, коннекторы, каналы, рантаймы |
| **bundle** | Только конфиг: джобы, инструкции, правила, скиллы — без кода | `frood/standard`, «Meeting Intelligence», «Personal PM» |

### Протокол модулей

- Каждая возможность — версионированный контракт, описанный OpenAPI / JSON Schema (`media.transcribe@1`, `sources.pull@1`, `notify.send@1`…).
- Контейнерный модуль при старте отдаёт ядру манифест и проходит проверку здоровья; ядро маршрутизирует вызовы возможностей.
- Модуль обращается к API Frood сервисным токеном со scopes из манифеста.
- Builtin-модули реализуют те же контракты, поэтому любой из них можно заменить контейнерным, кроме самого ядра.

## 3. Возможности и совместимость

- Версии контрактов — semver: несовместимое изменение = новая major-версия.
- Ядро поддерживает текущую и предыдущую major-версию каждого контракта.
- Для каждого контракта есть **набор тестов соответствия**; модуль прогоняет его в своём CI, ядро — при `frood plan` для локальных модулей.
- Разрешение при `plan`: для каждого `requires` нужен ровно один провайдер или явный выбор в конфиге (например, разные `llm.complete` для разных аккаунтов).
- Честная оговорка из 02: замена провайдера хранилища — это не одна строка; нужна миграция данных через экспорт и импорт (§8).

## 4. Реестр

(D7′.) Git-репозиторий с индексом:

```
registry/
  modules/google-drive/0.4.2.yaml   # манифест + digest образа + исходники + лицензия
  bundles/standard/1.2.0.yaml
  index.json
```

- Можно подключить несколько реестров (официальный, свой, компании) — как Homebrew taps. Сторонние реестры разрешены с v1 (QK1).
- Инсталляция фиксирует версии; **digest образа обязателен**; подписи (например, cosign) — опционально в v1, проверяются, если есть.
- `frood search`, `frood add`, `frood upgrade` работают с индексом.
- При установке `plan` показывает, что модуль просит: сеть, секреты, scopes API — и требует явного подтверждения.

## 5. Конфиг и жизненный цикл

`frood.yaml` описывает инсталляцию целиком: модули и версии, хранилище, вход (провайдеры, списки адресов), аккаунты, рантаймы, источники, джобы и правила, внимание и каналы, бэкапы, политики (в том числе какие данные в какие модели — G13). Где лежит файл — файл на сервере, git или push через API (W7′).

| Команда | Что делает |
|---|---|
| `frood init` | Создаёт заготовку конфига и секретов |
| `frood plan` | Проверяет схему, разрешает возможности, показывает diff с работающей инсталляцией, нужные миграции и запрошенные права модулей |
| `frood apply` | Разворачивает, мигрирует, проверяет здоровье, записывает ревизию конфига |
| `frood status` | Здоровье, версии, отставания |
| `frood upgrade` / `frood rollback` | Обновление и откат (§6) |
| `frood backup` / `frood restore` / `frood backup verify` | Бэкапы (§7) |
| `frood export` / `frood import` | Переносимый экспорт (§8) |

- **Цель деплоя — тоже модуль** (`deploy.target`): в v1 — Docker Compose на VPS (+ Caddy для TLS, Tailscale для админ-доступа); позже Helm для Kubernetes, «один бинарник + systemd» для минимальных установок.
- В режиме git ядро следит за веткой: `plan` → применяет сам, если изменение разрешено политикой, или создаёт запись Inbox «изменение конфига ждёт подтверждения».

## 6. Версии и обновления

- **Релиз платформы = BOM:** версия ядра + версии модулей по умолчанию + версии контрактов. Инсталляция выбирает релиз и может переопределять версии модулей.
- `frood upgrade --to 1.3`:
  1. `plan`: совместимость контрактов, миграции, изменения прав;
  2. автоматический снапшот перед обновлением (бэкап БД и конфига);
  3. миграции по схеме expand / contract, чтобы старая версия могла работать с новой схемой до завершения;
  4. проверки здоровья;
  5. при провале — автоматический откат; если миграция необратима — восстановление из снапшота.
- Данные и настройки сохраняются при обновлениях (01 §11); формат экспорта версионирован.

## 7. Бэкапы

(Детали и цены — 02 §11; здесь — как это ложится на платформу.)

- Тип модуля `backup.target`; реализации-примеры: restic или Kopia в S3-совместимое хранилище (B2, R2), Hetzner Storage Box, локальный диск.
- **Два независимых хранилища** по умолчанию в шаблоне конфига: защита от потери одного провайдера и от удаления VPS.
- **Что бэкапится:** согласованный бэкап БД (дамп или физический бэкап с WAL; PITR — по желанию), объектное хранилище (заметки, голосовые, записи встреч), ревизии конфига, данные модулей, у которых они есть.
- **Секреты — отдельно:** зашифрованы ключом восстановления, который хранится у пользователя вне сервера. Без него бэкап бесполезен постороннему.
- **Расписание и хранение** — из конфига (пример из 02: каждые 6 часов, дневные 30 дней, месячные 12 месяцев).
- **Проверка восстановления:** `frood backup verify` по расписанию поднимает временную копию из бэкапа и сверяет; провал — тревога в Inbox.
- Снапшот перед каждым обновлением (§6).

## 8. Переносимый экспорт

- `frood export` → формат, не зависящий от СУБД: JSONL событий журнала, утверждения со всей историей версий, сущности, Proposals и Verdicts, ссылки на источники и якоря, вложения файлами, `schema-version.json`; плюс человекочитаемый Markdown по сущностям.
- Назначение: приватный git, файл, другая инсталляция.
- `frood import` поднимает знания в инсталляции с другим провайдером хранилища — так делается «замена Postgres на что-то другое» (D1′).

## 9. Наблюдаемость

- **Логи:** структурированные (JSON) от ядра и модулей, с id запуска, события, трассы.
- **Трассы и метрики:** OpenTelemetry; контекст трассы передаётся и в MCP (`traceparent` в `_meta`, спека 2026-07-28 ✅). Метрики: отставание dispatcher, глубина очереди, длительность и ошибки запусков, расходы, возраст курсоров источников, результаты бэкапов.
- **Хранение:** по умолчанию лёгкое, внутри инсталляции (ограниченное по времени); внешние системы (Prometheus, Loki, Grafana и т.п.) — модулями-экспортёрами.
- **Админ-панель** (N9′) строится на этих данных; детекторы «заглохло» создают тревоги в Inbox.

## 10. Безопасность платформы

- Секреты — модуль `secrets.store`: зашифрованный файл (age / sops) по умолчанию, Vault или облачный KMS — по выбору.
- Модулю выдаются только объявленные секреты, сеть — только объявленная, API — только объявленные scopes.
- Цепочка поставок: digest вместо тегов, SBOM у официальных модулей, проверка подписей, если есть (урок LiteLLM, G8).
- Аудит всех вердиктов, изменений конфига, выдачи токенов, установок модулей.
- Политика данных: какие источники и виды данных можно отправлять в какие модели и рантаймы — в конфиге (G13).

## 11. Размер минимальной инсталляции

Ориентир, не смета: ядро + БД + Caddy помещаются на маленький VPS (порядка 2 vCPU / 4 GB). Локальное распознавание речи крупными моделями требует заметно больше ресурсов — на маленьком VPS разумнее облачный `media.transcribe`. Агенты в облачных рантаймах (Air, Managed Agents) не нагружают VPS.

## 12. Решения на ревью

| ID | Решение |
|---|---|
| K1 | Маленькое ядро — один бинарник на Rust (сервер + CLI): API, MCP, вход, Ledger, dispatcher и очередь, хост модулей, конфиг и секреты, миграции, сбор наблюдаемости. Остальное — модули |
| K2 | Модуль = манифест (возможности с версиями, схема настроек, права: сеть, секреты, scopes, события, миграции, здоровье) + реализация в одной из трёх форм: встроенный, контейнер (любой язык, HTTP), бандл (только конфиг) |
| K3 | Контракты возможностей версионированы (semver), описаны OpenAPI / JSON Schema, у каждого — тесты соответствия; ядро поддерживает текущую и предыдущую major-версию |
| K4 | Реестр — git-индекс модулей и бандлов; можно подключать несколько; версии фиксируются, digest обязателен, подписи опционально; права модуля подтверждаются явно |
| K5 | Жизненный цикл через CLI: init → plan → apply → status / upgrade / rollback / backup / restore / export. Цель деплоя — модуль; в v1 Docker Compose на VPS |
| K6 | Обновления: релиз = BOM; снапшот перед обновлением; миграции expand / contract; автоматический откат при провале проверок |
| K7 | Бэкапы: модуль `backup.target`, два независимых хранилища, БД + файлы + ревизии конфига; секреты отдельно под ключом восстановления у пользователя; регулярная проверка восстановления с тревогой |
| K8 | Переносимый экспорт и импорт в формате, не зависящем от СУБД (JSONL + Markdown + версия схемы) — для переноса и смены хранилища |
| K9 | Наблюдаемость: структурированные логи, трассы и метрики OpenTelemetry, связанные по запуску и событию; лёгкое хранение внутри, внешние системы — модулями; основа админ-панели |

### Лицензия: что подходит под «брать можно, продавать без исходников — нельзя»

| Вариант | Что разрешает | Что запрещает или требует | Open source (OSI)? |
|---|---|---|---|
| **AGPL-3.0** | Любое использование, в том числе коммерческое | Кто **изменил** код и даёт им пользоваться по сети, обязан открыть свои изменения. Развернуть **без изменений** и продавать хостинг — можно | да |
| **AGPL-3.0 + CLA (двойная лицензия)** | То же | То же; плюс вы можете продавать коммерческую лицензию тем, кто не хочет открывать изменения. CLA нужен, чтобы владеть правами на вклад контрибьюторов | да |
| **FSL-1.1** (Functional Source License) | Любое использование, кроме **конкурирующего коммерческого**: внутреннее использование компаниями, личное, некоммерческое | Нельзя продавать как продукт или сервис, заменяющий ваш. Каждый релиз через 2 года становится Apache-2.0 или MIT | нет (fair source) ✅ [fsl.software](https://fsl.software/) |
| BSL 1.1 / Elastic License 2.0 / PolyForm Shield | Похоже на FSL | Условия различаются от проекта к проекту; без автоматического перехода или с переходом через годы | нет |

- Буквально «коммерческое использование → публикуй исходники» — это AGPL. Но AGPL **не запрещает** развернуть немодифицированную версию и продавать хостинг.
- Буквально «нельзя просто взять и продавать» — это FSL. Но это уже не open source в строгом смысле (01 §12 говорил про «открытый проект»).
- Рекомендация: **AGPL-3.0 для ядра + Apache-2.0 для контрактов, SDK и официальных модулей + CLA**. Это настоящий open source, изменения у тех, кто строит на нём сервис, остаются открытыми, а сторонние модули могут быть под любой лицензией (общаются по HTTP и реализуют открытые контракты). CLA оставляет возможность двойной лицензии или смены лицензии позже. Если важнее запретить перепродажу совсем — FSL.

Источники: [fsl.software](https://fsl.software/), [A. Ronacher: FSL vs AGPL](https://lucumr.pocoo.org/2024/9/23/fsl-agpl-open-source-businesses/), [Safe: переход на FSL, 2026](https://help.safe.global/articles/4365429719-licensing-changes-faq).
