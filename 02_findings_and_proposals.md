# Найденные решения, архитектурные идеи и предложения ассистента

> Сводка **всех основных находок, вариантов и рекомендаций из предыдущих ответов** по проекту личной/корпоративной памяти и проактивных AI-ассистентов. В отличие от [документа с требованиями](01_user_requirements.md), здесь намеренно содержатся **предложения ассистента, а не только пожелания автора**. Повторяющиеся идеи объединены, а изменившиеся по ходу разговора рекомендации показаны как эволюция решения.
>
> Состояние обсуждения: **17 октября 2026 года**. Цены и функции сторонних проектов меняются. Ссылки в конце ведут преимущественно на первичные источники. Оценки сложности, сроков и архитектуры — **предположения**, а не подтверждённые характеристики будущего продукта.

## 1. Краткий вывод и развитие рекомендации

Изначально задача выглядела как «Second Brain» и поиск готовой долговременной памяти для AI. Затем она расширилась до проактивного ассистента, способного первым выходить на связь, а позднее — до **открытой модульной платформы, собираемой из заменяемых компонентов**.

Рекомендации тоже менялись:

1. **Быстрый прототип памяти:** OpenMemory / Mem0, опционально n8n.
2. **Более содержательная память:** Graphiti как temporal knowledge graph + PostgreSQL для истории и подтверждений + n8n для автоматизаций.
3. **Готовые ассистенты для изучения:** MIRA, Mimir, PersonalClaw; память для нескольких агентов — fleetmem.
4. **После уточнения требования независимости:** долговременная память и события должны жить отдельно от агентного продукта; агент — сменный исполнитель.
5. **После требования extensibility:** небольшой собственный Core, типизированные capabilities, контракты модулей, конфигурируемые providers и независимые deployments. Для выполнения фоновых задач: Hatchet или Windmill, а Graphiti — необязательная реализация модуля знаний.

**Последнее рекомендуемое направление:** небольшой собственный доменный Core + открытые контракты Memory API/MCP + event/decision store + подключаемые провайдеры выполнения, поиска, хранения и клиентов. Не пытаться на первом этапе создавать универсальный продукт из десятков микросервисов.

## 2. Предлагаемая логическая архитектура

```text
                      INPUT / INTEGRATIONS
              Voice · Text · Meetings · Slack · Docs
                              |
                              v
                     Ingestion / Parsing
                              |
                              v
                     Observations / Events
                              |
                    Extraction / Reasoning
                              |
                +-------------+-------------+
                |                           |
                v                           v
        Proposed changes              Agent work items
                |                           |
                v                           v
        Approval / Decision Inbox    Workflow / Scheduler
                |                           |
                +------------+--------------+
                             |
                             v
                   CANONICAL MEMORY CORE
            Facts · Sources · History · Decisions
                             |
              +--------------+--------------+
              |              |              |
              v              v              v
            MCP            HTTP         Read models
              |              |              |
         ChatGPT/Codex    Integrations   Search/Graph

                   OPTIONAL PROACTIVE CHANNELS
                    Telegram · Push · Slack
```

Здесь разделены:

- **Интерактивное использование:** внешний клиент запрашивает знания и предлагает новые записи.
- **Фоновая обработка:** система самостоятельно реагирует на события, время и изменения источников.
- **Память:** знания и ожидающие решения объекты существуют независимо от запуска агента.
- **Исполнитель:** Codex, Claude Agent SDK, Factory Droid, локальный агент или другой runtime обрабатывает задачу, не владея каноническими данными.
- **Каналы:** Telegram, веб, мобильное приложение и другие интерфейсы показывают пользователю данные, но не становятся их единственным хранилищем.

Основной принцип: **данные, правила и история постоянны; агенты, UI и workflow engines заменяемы**.

## 3. Предложенная модель знаний

### 3.1. Разделять наблюдение, предложение и подтверждённое изменение

Это одно из наиболее существенных предложений.

- **Observation:** новое сообщение, документ, голосовая запись или извлечённое свидетельство.
- **Proposal:** агент предполагает, что стоит создать, изменить, подтвердить или закрыть факт.
- **Accepted change:** решение, которое действительно меняет подтверждённое знание.
- **History:** журнал того, что изменилось, когда, кем и на каком основании.

Пример последовательности:

```text
Slack message observed
         |
         v
Candidate deadline change
         |
         v
Pending decision
         |
     +---+----+
     |        |
   Accept   Reject
     |        |
     v        v
   Update   Keep old
   memory   state
```

Предложенные ранее имена событий: `FactProposed`, `FactAccepted`, `FactChangeProposed`, `FactReviewRequested`.

### 3.2. Сохранять происхождение и степень определённости

В предлагаемых свойствах факта:

- Ссылка на первоисточник и место внутри него (сообщение, документ, эпизод встречи).
- Кто утверждал факт и кто подтвердил изменение.
- Момент появления информации в источнике и момент её обработки.
- Различие между «это обсуждали», «это предложили», «об этом договорились», «агент сделал вывод».
- При необходимости оценка уверенности модели **как индикатор**, не как гарантия истинности.

Без этого опасно автоматически превращать обсуждения в решения: фраза «а что, если перенести срок?» ещё не равна переносу срока.

### 3.3. Временная модель: valid time и transaction time

В предыдущих ответах обсуждалась **двухвременная (bitemporal) модель**, вдохновлённая подходом Graphiti:

- **Valid time:** когда утверждение действовало в реальности.
- **Transaction/recorded time:** когда система об этом узнала или записала.

Это позволяет спрашивать, кто отвечал за компонент на определённую дату и когда система узнала об изменении.

### 3.4. Управление жизненным циклом

Предлагались статусы/представления:

- `active` — актуально;
- `superseded` — заменено новой версией;
- `completed` — выполнено;
- `historical` — осталось в истории;
- `needs_verification` — требует перепроверки.

Важно **не архивировать всё связанное с закрытым проектом автоматически**. После merge блокер может стать историческим, а архитектурное решение — остаться актуальным.

Для переоценки предлагались три триггера:

1. **Прямая замена** информации новой.
2. **Изменение состояния проекта/задачи**: merge, релиз, закрытие эпика.
3. **Периодическая проверка** по правилу или `review_after`.

### 3.5. Event sourcing в разумных пределах

Предлагалось взять идеи **Event Sourcing + CQRS**, но не создавать сложную распределённую систему:

- PostgreSQL — каноническая история событий, решений и одобренных изменений.
- Удобное текущее представление знаний строится из истории.
- Поисковый индекс или граф — потенциально перестраиваемая проекция.
- Источники и вложения хранятся вместе с устойчивыми идентификаторами.

**Важная оговорка:** нельзя рассчитывать, что повторный прогон сырых данных через LLM точно воспроизведёт прежние факты. Для надёжного восстановления нужно хранить подтверждённые результаты извлечения и решения человека; миграции и построение индексов тестировать.

## 4. События, задачи, расписания и исполнители

В поздней рекомендации предложено **не называть всё одним event**:

- **Event** — что уже произошло (`source.updated`, `decision.resolved`).
- **Proposal** — какое изменение знаний предложено.
- **Task / Work item** — какую операцию должен выполнить исполнитель.
- **Schedule** — когда порождать очередное событие или задачу.
- **Decision** — сохраняемый объект, ожидающий ответа человека.

Примеры событий (предложенный словарь, не готовый стандарт продукта):

```text
source.updated
observation.captured
memory.change_proposed
memory.change_accepted
decision.requested
decision.resolved
review.due
```

В качестве переносимого **формата** внешних событий предлагался [CloudEvents](https://cloudevents.io/), а для документирования event-driven API — [AsyncAPI](https://www.asyncapi.com/). Это не замена оркестратору, очереди или модели доменных событий.

### Две схемы запуска

1. **По событию:** изменился источник → агент исследует контекст → предложит изменение → при необходимости появится решение.
2. **По времени:** каждую ночь проверка изменений с последней успешной обработки → дополнительные задачи → утром дайджест и вопросы.

Рекомендовано хранить **checkpoint последней успешно обработанной позиции**, а не рассчитывать только на интервал «за вчера»: после падения или пропущенного cron-запуска система должна уметь догонять пропущенное.

### Надёжность доставки и обработки

В финальных предложениях упоминались:

- Устойчивый журнал событий.
- Транзакционный **outbox** между изменением состояния и публикацией события.
- **Идемпотентные** задачи и уведомления, чтобы повторы не приводили к дублированию.
- Повторные попытки, история запусков и мониторинг ошибок.
- Сохранённые pending decisions независимо от живой сессии workflow.

Для маленького персонального инстанса на старте **не нужны Kafka, RabbitMQ или NATS**: могут хватить PostgreSQL, outbox и фонового worker. Отдельный durable workflow engine имеет смысл, когда сложность сценариев и ожиданий растёт.

## 5. Human-in-the-loop и проактивный интерфейс

### 5.1. Knowledge Inbox как Pull Requests

Сильная предложенная метафора: **агенты не переписывают знания бесконтрольно, а создают что-то похожее на pull requests**.

У предложения есть:

- Старое состояние и предлагаемое новое.
- Причина изменения.
- Ссылки на доказательства.
- Возможные связанные записи.
- Действия `Accept`, `Reject`, `Investigate` (или их аналоги).

Можно принимать очевидные изменения автоматически по настроенной политике, а существенные — отправлять на подтверждение. Автосохранение фактов, предложенных самим пользователем, обсуждалось как возможное упрощение.

### 5.2. Разделять изменение памяти и необходимость уведомлять

Не каждое найденное противоречие требует немедленного push. Предлагалось понятие **Actionable Insight** или `decision_required`: от пользователя требуется конкретное действие, и система понимает, почему именно его стоит беспокоить.

Обсуждавшиеся ситуации:

- Конфликт по дедлайну.
- Решение, которое зависло и требует реакции.
- Зависимость, по которой нет ответа.
- Приближение значимого срока.
- Возможный блокер.
- Переоценка знаний после завершения проекта.

Ассистенту полезно иметь модель **обязанностей, проектов, полномочий и приоритетов пользователя**, чтобы не присылать десятки нерелевантных уведомлений из всех доступных каналов.

### 5.3. Отдельный объект решения

Уведомление — **лишь способ доставить ссылку на вопрос**, а не место хранения ответа.

Например, агент обнаружил конфликт и записал `decision.requested`. Вопрос появляется в Inbox, может быть показан Telegram-ботом, открыт в вебе, обсуждён через Codex, а решение сохраняется в едином Core.

### 5.4. Минимальные экраны

Предлагались три самостоятельных интерфейса:

1. **Inbox:** новые факты, конфликты, вопросы и предложения об устаревании.
2. **Knowledge Explorer:** люди, проекты, решения, сроки, связи, история, источники.
3. **Activity Log:** хронология извлечений, предложений, изменений, проверок и ошибок.

Предлагалось **не создавать ещё один обязательный чат**: чатов достаточно в существующих агентах. Веб-интерфейс нужен в первую очередь для памяти и решений.

## 6. API и независимость от клиентов

**MCP** был предложен как основной протокол подключения совместимых агентов, а **HTTP API** — как стабильный первичный интерфейс для иных клиентов и интеграций. **CSV** может служить экспортом, но не полноценным API для событий и истории.

Пример предложенных операций:

```text
memory_search(query, filters)
memory_get_fact(fact_id)
memory_get_entity(entity_id)
memory_get_history(entity_id)
memory_get_context(topic)
memory_propose_fact(content, source)
memory_propose_change(fact_id, changes)
memory_list_pending()
memory_get_review(review_id)
memory_approve(review_id)
memory_reject(review_id, reason)
```

В более компактной поздней форме:

```text
search_knowledge(query, filters)
get_context(topic)
capture_observation(text, source)
propose_change(change, evidence)
list_pending_decisions()
get_decision(id)
submit_decision(id, answer)
```

**`get_context(topic)`** — не просто поиск по похожим документам, а краткое согласованное представление проекта: текущее состояние, ответственные, решения, блокеры, последние изменения и ссылки на источники.

Особенности безопасности API:

- Отдельные права на чтение, предложение изменений, подтверждение и запуск агентов.
- Подтверждение нельзя доверять любому подключённому клиенту.
- Для удалённого MCP учитывается аутентификация и авторизация; реализация зависит от клиентов.
- Поддержка custom MCP у конкретных приложений, особенно мобильных, должна проверяться отдельно: **возможность подключиться к MCP не универсальна для всех интерфейсов**.

## 7. Эволюция модульной платформы

### 7.1. Четыре понятия

В финальном обсуждении предложено различать:

| Понятие | Смысл |
|---|---|
| **Core** | Загрузка и жизненный цикл модулей, конфигурация, маршрутизация, события, безопасность |
| **Module Type / Contract** | Что модуль умеет и какой интерфейс предоставляет |
| **Provider / Implementation** | Реализация контракта конкретной библиотекой, сервисом или технологией |
| **Deployment** | Конкретно установленная система с выбранными providers, политиками и настройками |

### 7.2. Capability-based зависимости вместо технологических

Предложена идея делать **capability** главной единицей совместимости:

```text
storage.key_value
storage.transactional
storage.events
storage.objects
knowledge.search
knowledge.remember
knowledge.review
agents.execute
agents.resume
events.publish
events.subscribe
notifications.send
notifications.request_decision
sources.search
sources.subscribe
```

**Один provider может реализовать несколько capabilities**. Другой модуль зависит от нужной capability и её версии, а не от названия Postgres, Graphiti или конкретной библиотеки.

При этом нельзя честно обещать, что PostgreSQL, MongoDB и MySQL всегда заменяются одной строкой: различаются транзакции, запросы, модели данных и гарантии. Замена может требовать capability checks, конвертацию данных, миграции и иногда изменения архитектуры.

### 7.3. Категории подключаемых модулей

Предложенная классификация:

- **Infrastructure:** transactional store, object store, event store, workflow engine, LLM providers.
- **Domain:** personal memory, knowledge graph, decision inbox, task tracking, calendar intelligence, document indexing.
- **Integrations:** Slack, YouTrack, Google Drive, GitHub, Gmail, календарь, документы.
- **Agent runtime:** Codex SDK, Claude Agent SDK, Factory Droid, custom/local executor.
- **Agent definitions:** правила, задачи, разрешённые инструменты, триггеры, ожидаемый результат.
- **Client:** MCP adapter, HTTP adapter, web UI, Telegram, Slack, mobile, CLI.

Разделение `Agent Runtime` и `Agent Definition` принципиально: один ежедневный обзор можно запускать в разных агентных движках без смены описания задачи.

### 7.4. Пример контракта модуля

Ниже — **эскиз предложенного формата**, не существующая спецификация:

```yaml
name: knowledge-graph
version: 1.2.0
provides:
  - knowledge.search@v1
  - knowledge.entities@v1
  - knowledge.relationships@v1
requires:
  - storage.graph@v1
  - agents.execute@v1
config:
  extraction_model:
    type: string
  automatic_extraction:
    type: boolean
    default: true
events:
  consumes:
    - source.ingested
  produces:
    - knowledge.fact_discovered
    - knowledge.conflict_detected
```

Из деклараций зависимостей можно построить разрешение providers; из схемы настроек — интерфейс конфигурирования; из списков событий — проверку совместимости. Это пока **предложение архитектуры**.

### 7.5. Declarative deployment

Рассматривался манифест вида:

```yaml
apiVersion: memory.dev/v1alpha1
name: personal-assistant
modules:
  storage:
    provider: postgres
  knowledge:
    provider: graphiti
    graphStore: falkordb
  automation:
    provider: hatchet
  agents:
    provider: factory-droid
  notifications:
    provider: telegram
    token: ${secret:TELEGRAM_TOKEN}
  api:
    provider: mcp-http
automations:
  daily-review:
    schedule: '0 3 * * *'
    agent: knowledge-reviewer
policies:
  defaultAccess: deny
  automaticApproval: false
```

Возможные команды (также **только концепция**):

```bash
memoryctl deploy personal-memory.yaml
memoryctl upgrade
```

Ожидаемые функции контроллера: проверка схемы и зависимостей, версия компонентов, формирование deployment, миграции, health checks, обновления с сохранением данных. Для первого VPS предлагалось использовать **Docker Compose**, а для инфраструктуры — при необходимости **OpenTofu**.

### 7.6. Core должен быть маленьким

Предложено **не делать всё плагинами**. Семантическое ядро ограничить контрактами и жизненным циклом:

- Module registry, config loader, dependency/capability resolver.
- Event routing и доступ к durable state.
- Security context, identity и permissions.
- Lifecycle / version checks.
- HTTP/MCP adapters как подключаемая наружная граница.

Отдельный критерий архитектуры: Core должен быть способен стартовать **без LLM, Knowledge Graph и чата**.

Не создавать микросервис для каждого модуля в первой версии: модульность контрактов не требует множества процессов. Установка сторонних контейнеров и обновления требуют контроля доверия, изоляции и секретов; произвольная динамическая загрузка плагинов — не обязательна для MVP.

### 7.7. Bundles / пакеты возможностей

Позднее предлагались распространяемые наборы модулей, правил и автоматизаций:

- `Personal Project Manager` — управление договорённостями и зависшими решениями.
- `Meeting Intelligence` — извлечение решений из встреч и отслеживание исполнения.
- `Personal Life Assistant` — календарь, личные факты и напоминания.

Пакет декларирует нужные capabilities и устанавливается без ручного изменения Core.

| **[Graphiti](https://github.com/getzep/graphiti)** | Временные связи и эпизоды, извлечение знаний, обновление графа, MCP | Скорее memory engine; контролируемый approval workflow и независимый канонический журнал надо строить отдельно |
| **[Mem0](https://github.com/mem0ai/mem0)** / **[OpenMemory](https://github.com/mem0ai/mem0/tree/main/openmemory)** | Быстрый MVP общей памяти с MCP для разных клиентов | Сложный жизненный цикл договорённостей и ручное разрешение конфликтов не являются готовой основной моделью |
| **[Khoj](https://github.com/khoj-ai/khoj)** | Более готовый Second Brain, документы, поиск, автоматизации | Ориентирован на приложение/ассистента, а не на открытый доменный event/decision core |
| **[MIRA](https://github.com/Vexillon-ai/MIRA)** | Проактивные сообщения, память, фоновые агенты, каналы, голос, self-host | MCP host mode для подключения *внешних* инструментов не доказывает, что общая память доступна любому внешнему MCP-клиенту; публичная beta, небольшой проект |
| **[Mimir](https://github.com/csornyei/mimir)** | Human approvals, локальная память, morning briefing, ntfy | Скорее проект-референс и самостоятельный ассистент; не универсальное ядро |
| **[PersonalClaw](https://github.com/PersonalClaw/PersonalClaw)** | Provider-agnostic gateway, memory, knowledge, автоматизации, агенты | Pre-1.0, возможны breaking changes; наружу MCP доступен только для ограниченного набора read-only инструментов по текущему README |
| **[fleetmem](https://github.com/aurelius86/fleetmem)** | Независимая общая память через MCP/HTTP, роли агентов, knowledge graph, review queue | Нет встроенной общей инфраструктуры проактивных пользовательских каналов; маленький ранний проект |

### Что именно было выделено у Graphiti

- Temporal graph и инкрементальное добавление эпизодов.
- Представление сущностей, отношений и фактов.
- Поиск, сочетающий семантику и связи.
- Способность учитывать новые конфликтующие эпизоды.
- MCP-сервер; в версии документации v2 он назван экспериментальным.
- Использование FalkorDB или Neo4j в соответствующих конфигурациях/версиях.

**Корректировка прежней идеи:** если требуется approval **до** изменения канонических знаний, не нужно отдавать Graphiti безусловное право автоматически менять их. Предлагался слой proposals + одобрений + отдельная проекция графа.

### Что привлекло внимание в fleetmem

- MCP и HTTP интерфейсы.
- Управление видимостью записей и правами агентов.
- `supersedes`, `conflicts_with`, `depends_on` в типизированном графе.
- Очередь review и обслуживание памяти.
- Задачи, проекты, история сессий и аудит.

### Почему готовый ассистент — не окончательный ответ

MIRA, Mimir или PersonalClaw могут быть хорошими референсами и быстрыми прототипами. Но они начинают с **ассистента как центрального приложения**. Итоговое требование проекта обратное: **память, её история, события и ожидающие решения принадлежат собственной платформе**, а ассистентов можно менять.

## 10. Развёртывание, безопасность и изоляция

### 10.1. На чём размещать

Обсуждались три основных варианта:

1. **Один VPS**, например Hetzner: минимум администрируемых машин, Docker Compose с PostgreSQL, приложением, worker, возможно FalkorDB/Graphiti и workflow engine.
2. **Домашний сервер / Mac mini:** больше физического контроля; приходится решать доступность, питание, связь и обновления.
3. **Managed services:** меньше эксплуатации, но больше внешних сервисов, доверия и потенциального lock-in.

Пояснение из беседы: **self-hosted PostgreSQL на VPS** — это обычный контейнер или процесс на уже арендованной виртуальной машине. Сама PostgreSQL не требует платной лицензии, но VPS и диски оплачиваются.

### 10.2. Защита удалённого доступа

Предлагались:

- Приватная сеть (например, Tailscale) для администрирования.
- Отдельный HTTPS endpoint, если внешнему облачному MCP-клиенту он необходим.
- Сильная авторизация, ограниченные scopes и разные credentials по назначению.
- Раздельный доступ на чтение, proposal, approve и выполнение агентных действий.
- Шифрование резервных копий и защищённое хранение ключей.
- Минимальные секреты у фоновых исполнителей; сетевые ограничения.

**Self-host на чужом VPS не даёт криптографической гарантии, что провайдер никогда не получит доступ к работающему серверу.** При использовании внешних LLM API данные, отправленные модели, также уходят за пределы собственной инфраструктуры.

### 10.3. Personal и Corporate как отдельные deployments

Предложено использовать **один код платформы, но отдельные установки**, когда рабочие и личные данные требуют строгой изоляции:

```text
Same source code
    |
    +-- Personal deployment -> personal storage, credentials, models
    |
    +-- Corporate deployment -> company network, approved storage/models
```

Политики могут ограничивать источники, модели, инструменты, разрешённые операции, доступ агентов и места обработки. В корпоративном варианте принципиально важно соблюсти правила работодателя; личный VPS не означает разрешение выгружать туда внутренние документы.

**OPA** предложен как возможный Policy-as-Code слой, но правила должны быть подкреплены фактической изоляцией, credentials и запретами исходящей сети. Агенту с одновременным доступом к рабочему и личному доменам нельзя автоматически доверять сохранение информационной границы.

## 11. Резервные копии и независимый экспорт

### 11.1. Вариант с минимальным количеством инфраструктуры

В конце обсуждения самым простым вариантом выглядело:

```text
VPS -> pg_dump / consistent DB backup
    -> Restic (encrypted backup)
    -> Cloudflare R2 or Backblaze B2
```

Для Google Drive можно использовать **Restic + rclone**. Предлагались также резервные копии в двух независимых хранилищах.

### 11.2. Что резервировать

- Каноническую PostgreSQL базу: факты, события, proposals, решения, историю.
- Исходные документы, аудиозаписи и другие вложения.
- Конфигурацию платформы и версий модулей.
- Данные графа/индекса, **если** их нельзя гарантированно и детерминированно перестроить из канонических сохранённых данных.
- Секреты и ключи восстановления — **отдельно и безопасно**, не в обычном незашифрованном архиве.

Для работающего PostgreSQL не нужно просто копировать каталог БД на лету: использовать согласованный `pg_dump` или специально настроенное физическое резервирование/PITR.

### 11.3. Пример ранее предложенной политики

- Согласованный бэкап PostgreSQL каждые **6 часов**.
- Ежедневные версии на **30 дней**.
- Ежемесячные версии на **12 месяцев**.
- Отдельные копии вложений и конфигураций.
- Регулярные **тесты восстановления** на временном сервере.
- Инструкция аварийного восстановления и пароль Restic вне VPS.

Это **пример политики**, не обязательная конфигурация. Для уменьшения возможной потери до минут предлагался PITR с архивированием PostgreSQL WAL.

### 11.4. Обсуждавшиеся хранилища

| Вариант | Плюсы | Минусы / нюансы |
|---|---|---|
| **Google Drive** | Может не потребовать доплаты при имеющемся свободном объёме; rclone поддерживает подключение | OAuth credentials на VPS, лимиты API; обычная история файлов не равна защищённому immutable backup |
| **Cloudflare R2** | S3-совместимый API; Restic напрямую; free tier | Ограничение бесплатного объёма; нужна отдельная продуманная защита от удаления |
| **Backblaze B2** | S3 API; первые 10 GB бесплатны; поддерживает Object Lock | Нужно внимательно проверить режим retention и полномочия выданных ключей |
| **Hetzner Storage Box** | Простая отдельная копия рядом с VPS | Тот же провайдер; не заменяет независимую внешнюю копию |
| **Приватный GitHub** | Удобен для текстовых export / JSONL / Markdown | Плохой основной backend для регулярных бинарных SQL dump: Git-история растёт, лимиты файлов; приватность репо — не end-to-end encryption |
| **Личный компьютер** | Дополнительная независимая копия | Нужно обеспечить регулярное копирование и сохранность устройства |
| **OneDrive / Dropbox / Oracle Object Storage** | Дополнительные возможные направления | Бесплатные лимиты, API и эксплуатационные условия нужно отдельно проверять |

### 11.5. Подтверждённые ориентиры по двум облачным хранилищам

На дату обзора в официальных документах:

- **Cloudflare R2 Standard:** **10 GB-month** хранения бесплатно каждый месяц, **1 млн Class A** и **10 млн Class B** запросов, бесплатный egress; затем стандартное хранение **$0.015 за GB-month**. Бесплатный объём не распространяется на класс Infrequent Access. Источник: [R2 Pricing](https://developers.cloudflare.com/r2/pricing/).
- **Backblaze B2:** первые **10 GB** хранения бесплатно; сверх лимита действуют текущие тарифы поставщика. Источник: [B2 pricing](https://www.backblaze.com/cloud-storage/transaction-pricing).

**Важное уточнение к ранним ответам:** у Cloudflare R2 действительно существуют **Bucket Locks**, защищающие объекты от удаления и перезаписи в течение retention периода. Однако у R2 нет полной совместимости с AWS S3 Object Lock API, а администратор конфигурации R2 может управлять правилами bucket lock. Поэтому до того, как называть такой бэкап гарантированно immutable при компрометации аккаунта, нужно отдельно проверить модель угроз и права ключей. Источники: [R2 Bucket Locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/), [S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/).

### 11.6. Экспорт знаний независимо от СУБД

Важная рекомендация: **помимо технического дампа** делать переносимый логический экспорт:

```text
export/
  events/*.jsonl
  facts/*.json
  decisions/*.json
  sources/...
  attachments/...
  schema-version.json
```

Так можно перенести память через годы, даже если не останется исходного движка Graphiti/n8n/другого модуля. Зашифрованный GitHub-репозиторий может быть удобным местом **для такого экспорта**, но не основным хранилищем бинарных дампов.

## 12. Оценки расходов из предыдущих ответов

Это **не смета** и не гарантированные цены. Оценки были сделаны для одного небольшого личного VPS и использования внешних LLM. При новой модульной архитектуре дополнительный workflow engine или несколько тяжёлых сервисов могут потребовать больше RAM.

| Конфигурация | Ранее обсуждавшийся ориентир / месяц |
|---|---:|
| Маленький MVP, мало обработки | **€10–18** |
| Умеренная фоновая обработка источников | **€20–41** |
| Интенсивные агенты и большие объёмы данных | **€49–110+** |
| Общий практический ориентир, который тогда предлагался | **€15–40** |

Ранее приводилась примерная разбивка:

- VPS порядка **€8–15** в месяц за небольшую виртуальную машину, без привязки к гарантированному актуальному тарифу.
- PostgreSQL, Restic, Graphiti, FalkorDB и некоторые workflow-движки в self-host конфигурации — без отдельной платы за лицензию, **но** оплачиваются ресурсы и эксплуатация.
- LLM API — условно **€2–20** для умеренного объёма, но число проходов, длина контекста, агентный веб/Slack-поиск и дорогие модели способны изменить это в разы.
- Embeddings, транскрипции и резервные копии — обычно небольшая дополнительная статья для текстовой персональной базы, но зависит от нагрузки.
- R2/B2 при суммарных бэкапах в пределах актуальных бесплатных лимитов могут не добавлять стоимость хранения.

Предлагалась экономия: **инкрементальная обработка** изменившихся данных, дешёвая классификация прежде дорогого анализа, повторные проверки только для значимых фактов, ночные пакетные задачи. Не прогонять всю историю источников через LLM каждый день.

### Трудозатраты — ранняя оценка для прототипа

Ранее была приведена крайне приблизительная оценка **5–12 рабочих дней** для ограниченного прототипа Graphiti + события + первые источники + простой Inbox + безопасность, при активном использовании coding agents. Это **не оценка готовой extensible-платформы**: модульные контракты, миграции providers, isolation, тесты совместимости, package manager и безопасные upgrades существенно расширяют проект.

## 13. Предлагавшиеся планы внедрения

### 13.1. Быстрый MVP без полноценной платформы

1. Поднять OpenMemory либо Graphiti локально.
2. Подключить хотя бы одного агента через MCP.
3. Добавить ручное внесение знаний текстом и голосом.
4. Проверить сохранение, поиск и изменение фактов.
5. Постепенно добавить источник вроде YouTrack/Slack, расписание и уведомления.

Цель такого пути — **проверить полезность памяти**, а не создать сразу окончательный фреймворк.

### 13.2. MVP, подготовленный к модульности

1. Определить минимальный контракт Core, capabilities и одну реализацию каждого контракта.
2. Сделать PostgreSQL каноническим хранилищем истории, фактов и ожидающих решений.
3. Сделать Memory API и MCP adapter.
4. Подключить один runtime агента и один движок фоновых задач (например, Hatchet).
5. Реализовать ingestion одного источника и одну ночную проверку.
6. Реализовать Decision Inbox и один канал уведомлений.
7. Добавить экспорт и автоматический проверяемый backup.
8. Только затем вводить второй provider того же типа, knowledge graph, реестр модулей, auto-deploy и пакетную дистрибуцию.

### 13.3. Сквозной тест, предложенный как архитектурный критерий

**Записать договорённость через один клиент → прочитать через другой → фоновым агентом обнаружить противоречие → перезапустить сервер → увидеть сохранившийся вопрос → принять решение.**

Тест должен проходить независимо от конкретного UI и агентной сессии.

### 13.4. Три дополнительные проверки расширяемости

- Новая функциональность устанавливается без изменений Core.
- Provider можно заменить без переписывания потребителей его **контракта**, с отдельной проверкой миграции данных.
- Один и тот же код разворачивается в личной, локальной и корпоративной конфигурации с разными разрешениями и компонентами.

## 14. Чего предлагалось не делать

- **Не делать векторную БД единственным источником истины:** similarity search не отвечает на вопрос, что сейчас действительно утверждено и почему.
- **Не сохранять всё, что сказал агент, как подтверждённый факт:** нужен отдельный процесс предложений и подтверждений.
- **Не вести всю память в одном огромном Markdown:** история, связи и изменения потребуют сложной обвязки; Markdown полезен как представление или экспорт.
- **Не запускать Kafka/Kubernetes/NATS только ради модульности:** маленькая система может жить в одном приложении и нескольких контейнерах.
- **Не связывать память с agent session или конкретным ботом:** исчезновение агента не должно уничтожить решения и историю.
- **Не проектировать универсальную абстракцию поверх любой СУБД без ограничений:** контракты должны отражать реальные гарантии и capabilities.
- **Не считать наличие MCP универсальной интеграцией со всеми продуктами:** каждый внешний клиент должен реально поддерживать нужный способ подключения.
- **Не путать self-hosting с полной недоступностью данных для провайдера облака или внешней LLM.**
- **Не проектировать сразу полноценный marketplace и горячую загрузку стороннего кода:** это отдельные задачи безопасности и совместимости.

## 15. Открытые вопросы и ограничения предложенной архитектуры

Следующие вопросы ранее поднимались или логически следуют из описанных предложений; **они не решены**:
